# 产品目标与首个能力增量

状态：Architecture v0 草案，2026-09-26。本文表达产品意图与验收方向，不声明实现完成。

## 目标

将值得解决的问题转化为经过验证、可以交付和维护的产品能力，减少等待、重复劳动、返工与人工协调。人主要负责方向、优先级、关键取舍和验收；系统在有效授权内持续推进工作。

质量包含产品价值、设计质量、实现正确性以及交付维护能力。质量和授权要求是约束；在满足约束的候选方案中比较时间、成本和人工投入。不采用一个可用低成本抵消质量失败的综合分数。

## 问题与目标使用者

跨项目使用 Agent 时，工程师反复搬运上下文、重建任务进展、核对工具输出，并在实现、CI、审查和实际使用之间协调。单次会话完成或一个 PR 变绿，不能独立回答最初的能力是否已经交付。

初始使用者是维护多个仓库、已有 Git/GitHub 工作流的工程师，以及共同执行和验收任务的人与 Agent。首个场景是自用工程交付；团队或商业产品定位需要真实使用结果支持。

系统应帮助使用者完成三类工作：将意图转成有边界的任务；在既定约束内持续执行并正确恢复；用版本明确的证据判断能力完成情况。稳定的项目知识从仓库取得，实际进度和运行证据由任务及执行记录维护。

## 非目标

首版不建设 Git 托管平台、CI/CD 替代品、通用 Agent 框架或项目管理 SaaS；不把核心领域模型限制为某个执行器的包装。确定性工具能够完成的工作继续使用确定性实现。

## 产品边界

| 组成 | 责任 |
| --- | --- |
| `kb` | 工程知识、规范、Failure Model 与方法论的长期来源 |
| Daedalus | 目标到工作的组织、上下文解析、执行协调、恢复、证据关联和能力验收 |
| Repository Delivery Workflow | 仓库内 PR、检查、审查、合流准入、集成与发布过程 |
| 执行器与工具 | 在指定环境和权限内完成研究、实现、测试或专业判断 |
| `atlas` / 其他平台 | 按需提供运行环境、计算、制品与观测能力 |
| `cxx-init` / 其他消费项目 | 维护自身契约和质量入口，使用适合自己的工程 Profile |

复用成熟的 Agent 执行循环、Git、CI 和发布设施。自主建设集中在跨这些设施的任务语义、证据适用性、恢复与能力验收。首个可用系统先服务自己的工程任务；对外产品需求另行验证。

## 工作尺度

一个 Capability Increment 是使用者能够辨认和验收的能力，例如“支持 Kafka 数据输入”。它可以包含多个任务和多个语义内聚的 PR。

PR 是仓库层面的原子变更单元，应有清晰意图、可理解差异、验证依据与回滚方式。能力验收覆盖这些变更的实际组合及最终使用路径。PR 合入是集成事实，不能单独证明能力完成。

系统包含相互连接的探索、交付和改进循环。探索可以推翻假设或终止方案；交付产生可用能力；实际反馈推动产品和交付系统继续改进。

## 第一条纵向切片

在一个已有 Repository Delivery Workflow 的仓库中完成一项真实能力增量：

1. 固定 Capability 的范围、非目标、验收条件、授权与预算；明确目标使用者和最终交付形态。
2. 建立 Task，解析项目契约、固定版本的 Profile、依赖和验证入口。
3. 创建 Attempt，绑定执行器、基线版本、隔离工作区和环境，完成实现及范围内修复。
4. 调用仓库本地验证入口，保留过程事实和候选版本，形成可审查 PR。
5. 由现有工作流完成 CI、语义审查及合流准入；Daedalus 记录外部状态。首版支持由人完成合并，自动合并不是前置要求。
6. 核对实际集成提交、所需制品或部署，在该对象上完成能力验收并保留结论。

PR 可以按仓库约定提前建立为 Draft，流程不要求实现完成后才创建。第 4 步是可独立检查的中间成果；第 6 步完成后才可声明整个纵向切片完成。

## 首个切片的验收要求

| 关注点 | 所需结果 |
| --- | --- |
| 可接入 | 新会话能找到适用契约、版本、环境及实际可运行的验证入口 |
| 可执行 | 一个真实任务能在隔离工作区中完成，执行事实归属于稳定 Task / Attempt 标识 |
| 可核对 | 能从 Capability 追溯到 Task、候选变更、PR、CI、集成版本及验收记录 |
| 守边界 | 本地检查和模型总结不替代仓库权威门禁；关键规则变化有明确处理 |
| 可恢复 | 中断与外部结果未知能够被识别、核对并继续处理，不覆盖已有工作或盲目重试 |
| 真正交付 | 对实际集成版本运行使用路径；需要安装、制品或部署的能力提供对应证据 |
| 可评估 | 记录人工介入、总耗时、失败尝试、验证及资源成本；缺失测量明确为未知 |

最小失败场景见 [架构文档](architecture.md)。首次真实消费项目及具体能力尚待选择；优先选择已有交付门禁、验收明确、结果可重现的项目。不能仅用格式修改证明完整系统有效。

## 建设顺序

| 阶段 | 交付能力 | 验收重点 |
| --- | --- | --- |
| Architecture v0 | 领域模型、责任边界、首个切片与失败场景 | 设计一致，可用于制定实现任务 |
| A：完整交付闭环 | 单项目、首个执行器、仓库工作流接入、能力验收 | 一项真实能力从目标走到可用成果；包含最小恢复与核对机制 |
| B：自治与恢复 | 更完整的恢复、取消、预算控制和异常处理 | 故障注入后可预测，重复副作用可发现并处理 |
| C：多项目与调度 | 多 Profile、多环境、执行器选择和依赖并行 | 提高合格交付效率，减少人工协调 |
| D：持续优化 | 代表性任务评测、工具升级验证、瓶颈分析 | 改进收益有可比较证据，质量没有退化 |

Daedalus 应逐步成为自身交付系统的消费者，并用外部消费项目检验抽象。目前处于文档引导阶段，不能声称仓库已经具备完整自治门禁。

## 效果评估

比较从目标明确到能力验收的耗时、人工投入、返工与缺陷、恢复成功情况和每项合格交付总成本。失败尝试、CI、计算资源与人工复核均计入成本；任务样本和环境差异应说明。资源选择的评估单位包括执行器、工具、上下文与运行环境，不能仅比较模型名称或 Token 单价。

首版暂不选定 CLI 形态、数据库、Web UI、常驻多 Agent 调度或生产自动发布。这些设计由实际切片需要驱动。
