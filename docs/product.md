# 产品契约与能力建设

状态：Architecture v0 产品契约草案，2026-09-26。依据项目发起者的完整工程系统核心指南；本文保存稳定产品意图，设计评审与实际进度记录在 PR / 任务中。

## 使命与设计依据

Daedalus 是 Agent-native Engineering Delivery System，一套由人、Agent、工具、知识、计算资源和成熟平台共同构成的工程系统。

> 将一个值得解决的问题，转化为经过验证、可以交付、能够维护的产品能力；尽可能减少等待、重复劳动和人工协调，同时持续提高产品与工程质量。

先设计完整系统的目标架构，再按可验收的能力增量建设。仓库约定、任务契约、执行协调和证据验证是组成部分；首个切片决定第一步投入，不能替代或缩小终态。自研软件可以很薄，整个系统仍须承担探索到运行反馈的完整责任。

核心指南中的产品原则是文档对齐依据；具体工具组合是候选接入基线，需通过实际任务核验。工具的品牌、数量、自动化比例与代码产量都不是产品目标。

## 四维质量与优化目标

以下四个维度必须同时满足，不能以某一维的高分抵消另一维的失败。

| 维度 | 必须回答的问题 | 所需结果 |
| --- | --- | --- |
| 产品价值 | 是否解决正确的问题，使用者是否真正受益？ | 明确场景、可使用能力、真实反馈 |
| 设计质量 | 架构是否适合问题，复杂性是否必要？ | 清晰边界、不变量、经过比较的取舍 |
| 实现质量 | 行为、性能与安全是否满足要求？ | 可复现验证、边界与失败测试、资源测量 |
| 交付与维护质量 | 能否安装、运行、升级、诊断和恢复？ | 可用制品、运行观测、升级与恢复路径 |

质量、安全和授权要求是约束。在满足约束的方案中，优化需求到可用能力的时间、每项合格交付的人工精力、缺陷与返工，以及包含工具、计算和维护的总成本。编译成功和 PR 合并只是部分工程事实。

## 问题、使用者与人的责任

工程师常常需要搬运上下文、催促执行、核对结果、恢复中断，并在产品判断、实现、CI、审查和实际使用之间反复协调。局部步骤完成仍可能没有交付真正需要的能力。

初始使用者是维护多个项目的工程师及协作团队，首个场景利用既有 Git/GitHub、macOS、C++/Rust 工程基础。长期产品定位依赖真实使用反馈，不从自用有效直接推断商业需求。

系统承担范围内的推进与核对；人集中处理产品方向、优先级、关键设计取舍、例外和验收。必要时使用领域专家、成熟服务和专用计算，成本与授权明确进入任务约束。

## 三个相互连接的循环

| 循环 | 输入与工作 | 输出及回流 |
| --- | --- | --- |
| 探索 | 问题、场景、约束；研究、原型、方案比较、风险实验 | 澄清的目标、关键取舍、验收条件；也可证伪或放弃方案，不要求生产代码 |
| 交付 | 足够明确的能力契约；实现、测试、修复、集成、打包和交付 | 可用成果及能力验收；新发现可返回探索调整目标 |
| 改进 | 使用反馈、线上问题、性能成本、交付摩擦和 Agent 失败 | 产品改进或工程系统改进，经优先级判断进入新的探索或交付 |

三个循环共享版本化知识、任务组织、资源选择、授权、状态、证据和评估。持续改进包含测试、环境、Skills、任务路由及资源配置；运行反馈不是交付结束后附带的一份报告。

## 完整能力增量与自治

工作方式为：**完整能力增量＋批内自主修复＋集中验收**。例如“支持一种新数据输入”覆盖接口、实现、错误处理、测试、配置、文档与必要的性能验证。

每个增量至少明确目标、非目标、验收条件、依赖、授权范围和资源预算。稳定信息从项目环境与 Profile 解析，不要求使用者反复填写。预算包含运行时间、重试、并发、模型、CPU/GPU、存储及人工投入。

增量内部自主读取上下文、制订与修订计划、调用工具、实现、测试、诊断、处理审查意见、复验和整理交付。遇到无法自行消除的目标歧义、关键契约变化、权限或预算扩展、不可接受风险，或需要产品与架构判断时，汇总事实与可选方案交给责任人。复用有效授权，避免逐个动作重复确认。

一个能力可以包含多个语义内聚、分别可集成和回滚的 PR。仓库合流与能力验收处于不同尺度；探索和判断任务也可以不产生 PR。

## 产品边界与资源原则

| 组成 | 责任 |
| --- | --- |
| 人与产品工作 | 价值判断、优先级、关键取舍、例外及验收 |
| Daedalus 控制面 | 连接三个循环；组织能力和任务、解析上下文、分配资源、管理执行恢复、关联证据和评价效果 |
| `kb` 等知识源 | 工程规范、Failure Model、设计依据和方法论 |
| Repository Delivery Workflow | 仓库内验证、审查、准入、集成和发布机制 |
| 执行器、工具与专家 | 在指定边界内执行研究、实现、验证和专业判断 |
| `atlas` / 其他平台 | 按需提供计算、制品、运行和观测能力 |
| 消费项目 | 拥有自身契约、验证入口、交付与运行要求 |

GitHub、Codex、CI、云计算与多 Agent 都可替换。优先复用成熟能力，自研必要的跨平台、跨任务语义。首版不重建 Git 托管、CI/CD、通用 Agent 框架或项目管理 SaaS，也不以 LLM 重写确定性工具。

资源选择评估 **模型 × 执行框架 × 工具集合 × 上下文 × 运行环境**。默认一个明确任务负责人，按真实可并行边界增加角色；审查拥堵时优先解决复核和集成瓶颈。机械工作使用确定性程序，复杂问题可投入强推理、实验、专家与专用环境。跨平台行为和性能结论必须在适用环境中验证。

## 第一条纵向切片

在一个真实项目中形成三个循环的最小实例，范围以 G2 切片契约确定：

1. 从真实问题和使用场景出发，验证必要假设，确定能力目标、取舍及四维质量的验收条件。
2. 建立 Task，解析版本化上下文、Policy / Profile、依赖、环境、执行器、授权与预算。
3. 在隔离工作区完成实现和自主修复，取得本地快速反馈与独立候选验证。
4. 通过项目既有交付工作流形成可审查变更、完成语义审查和集成；保存实际集成版本及证据。
5. 按产品类型形成可用制品或其他交付对象，在真实使用路径上完成能力验收，核对安装、配置、诊断与恢复要求。
6. 在约定观察窗口取得使用或运行反馈，记录质量、人工投入和总成本，作出继续、修复或暂不行动的判断，并将必要工作关联到下一循环。

PR 可以提前建立为 Draft；自动合并不是首个切片的前提。需部署的服务走受控发布；库、CLI、文档项目采用各自的分发与使用路径。反馈可能促使修订既有判断，但不抹去历史验收记录。

## 切片验收与阶段建设

| 切片验收面 | 所需证据 |
| --- | --- |
| 问题与价值 | 场景、用户目标、取舍、真实使用反馈及对应判断 |
| 设计与接入 | 适用契约、版本、关键不变量、项目自有验证入口与资源依据 |
| 执行与恢复 | Task / Attempt 事实、边界与失败案例、未知副作用核对 |
| 验证与交付 | 实际版本、独立检查、语义判断、可用对象及能力验收记录 |
| 维护与改进 | 诊断恢复依据、观察窗口、反馈处置、人工投入与总成本 |

先经过工程约定中的 G0 / G1 / G2 设计审查，再进入实现。建设阶段描述投入顺序，不将后期能力从目标架构中删除：

| 阶段 | 交付能力 | 验收重点 |
| --- | --- | --- |
| A：完整交付闭环 | 一项真实能力从问题走到可用成果、验收和初始反馈 | 三循环最小实例；含基本恢复和副作用核对 |
| B：自治与恢复 | 批内自主修复、状态恢复、受控交付、异常集中呈现 | 中断、超时、失败和未知结果得到正确处理 |
| C：多项目与资源调度 | 多 Profile、多环境、执行器路由、依赖并行及预算控制 | 合格交付更快，人工负担没有增加 |
| D：持续优化 | 工作流评测、工具升级验证、瓶颈分析和缺陷反馈 | 改进收益可测量，质量不退化 |

## 效果评估

代表性案例覆盖真实功能增量、难定位缺陷、跨平台问题，以及明确的失败与恢复要求。文档与格式修订不能单独证明整个系统有效。

每项合格交付记录总时间、等待时间、人工介入、缺陷返工、恢复结果、模型工具计算成本和维护投入。失败尝试与复核同样计入；缺失数据标为未知。比较时固定或说明任务集、质量标准、工具版本、上下文、环境和预算差异。

工具、模型、Skills 与环境升级先在代表性任务上比较成功率、成本、介入和退化，再决定是否成为默认。排行榜用于筛选候选，不能替代本项目评估。先以可测量的人工策略实现资源选择，按证据逐步自动化。
