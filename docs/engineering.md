| 载体 | 负责内容 |

| 本文 | Daedalus 的工程 Profile、开发验证方式及项目差异 |
| [AGENTS.md](../AGENTS.md) | 上下文导航与执行约定 |

这些文档按职责确定适用性。更具体的任务不能静默覆盖已接受契约；需要改变契约时，显式提出变更并同步相应文档或 ADR。草案不因公开或提交到 Git 就自动成为已评审接受的架构；用户明确的新要求可以发起契约修订。

Git/GitHub Workflow 的权威范围是仓库交付，其采用关系不能将 Daedalus 的产品目标缩小为 PR 流水线。核心指南决定完整系统的方向；具体工程规范在各自范围约束实现。发现冲突时记录适用范围、依据及变更决定，不能默默覆盖任何一方。

README 保留项目入口和成熟度。架构描述状态及转换规则，不记录某个任务今天的状态；PR 状态、检查结果和进行中工作保留在 GitHub 或执行记录中。共享规范只引用版本和采用关系，不复制维护第二份正文。

## 仓库结构与开发环境

文档基线保留六个入口：`README.md`、`AGENTS.md`、`docs/product.md`、`docs/architecture.md`、`docs/engineering.md`、`docs/adr/README.md`。ADR 在发生重要取舍时增加；协议文档和 Schema 在出现稳定接口消费者时再拆分。

文档使用 UTF-8 Markdown、相对内部链接和 Mermaid 概念图。当前没有应用源码、指定实现语言或工具链，也没有应用构建、测试与运行命令。语言、依赖和生成代码策略由首个实现切片的需求决定；选择时记录理由，固定必要版本，并明确生成源和更新入口。

## Architecture v0 Design Review

架构设计通过以下三个 Gate 组织审查，关注反例、矛盾、空洞和过早抽象。Gate 是推进所需的评估与决策，不是新增三个静态状态文件；结果绑定被审查的提交，记录在 PR / 任务中。

| Gate | 必须审查 | 通过所需结果 |
| --- | --- | --- |
| G0 — Product Contract | 使命、四维质量、三循环、Capability、范围、自治与效果指标 | 产品契约足以指导设计，第一切片没有替代终态 |
| G1 — Domain & Control Model | 系统边界、ID / revision / 不可变记录、Event / Fact / State、Attempt 连续性、Change Revision、Authority、Evidence applicability、外部副作用、恢复及运行反馈 | 对具体场景和反例得到一致解释，关键未决项有明确处理，模型可作为 G2 输入 |
| G2 — First Vertical Slice Binding | 真实消费项目与能力、执行器、Workflow、环境、最小持久化、source / revision / digest、验收与反馈窗口、预算 | 每一项系统责任有实际承担者和可验证接口，形成可执行切片契约 |

G1 审查至少走查架构中的版本改变与运行任务处置、退出码为 0 但产出缺失、断连与写入所有权不明、进程死亡、未知副作用、证据的信任 / 完整性 / 覆盖差异、相矛盾证据，以及契约观察窗口和运行退化案例。G2 选择最少必要技术，不提前绑定语言、数据库、守护进程或 UI。

每个 Gate 的结论包含基线、覆盖、阻塞项、取舍、判断依据和接受责任；文档齐全或格式通过不能自动令 Gate 通过。确有需要时可以做有边界的验证原型，但应先明确实验问题与范围，不把它视为正式切片实现已获放行。

在合理替代方案、权衡与接受依据明确后再创建 ADR；不批量生成 Accepted 记录。任何尚未完成的设计审查都保持为未完成，不能从“已提交 PR”推定架构 Baseline 已被接受。

## 文档阶段的验证

每次文档修改检查：本地链接及锚点、代码围栏、尾随空白、文件末尾换行，以及术语、对象关系和职责是否一致。新增且未跟踪的文件必须单独检查，不能只运行忽略它们的 `git diff --check`。

对已有基线的工作分支，确认实际集成基线后检查整个变更，例如 `git diff --check origin/main...HEAD`；提交前同时检查暂存区。初次提交没有父版本时，逐文件检查完整内容，再检查实际暂存集合。

架构审查按产品目标、架构驱动因素、系统上下文、领域模型、生命周期、信任与失败边界、合理替代方案和不变量推进。链接与格式通过不等于架构验收。验证报告留在本次任务或 PR 中，不复制为静态的“已通过”架构段落。

本仓库自身逐步使用相同体系：以文档设计能力为当前交付对象，明确契约、进行反例走查、保留检查与评审依据，再决定接受。它验证文档协作流程，不能代替真实功能、故障定位、跨平台及恢复案例对整个系统的验收。

当前尚无 `task quality`、仓库检查脚本或 CI。引入可执行能力时，再建立仓库自有验证入口，供本地与 CI 调用，并覆盖架构中的失败与恢复场景；命令成功、退出状态、日志和受测版本应可关联。性能实验需要固定输入、环境、正确性基线与测量方法。

未来持久化格式或外部接口发生兼容性变化时，应说明迁移与恢复方式。工具或依赖升级需运行受影响的代表性验证。上述约定不预先指定实现技术，也不声称当前具有这些检查设施。

## 初始化与后续交付

首次创建空远端时，在用户授权下将已检查的文档作为 bootstrap 提交建立 `main`。这一步建立初始基线，不视作已经完成 CI、Ruleset 或架构审查的证明。后续变更采用短期分支和 PR；保护规则、必需检查与审查身份需要独立落实和验证。

公开同步仅包含项目文档和后续明确纳入的工程资产。私人会话、机器绝对路径、凭据和临时执行记录不属于公共文档依赖。远端地址、提交与运行状态以 Git / GitHub 实际事实为准。

## Baseline、Profile、Instance 与 Adapter

共享 Core 表达跨项目的领域、证据和授权语义；Baseline 是选用规范的固定来源。Core / Profile / Instance 是语义复用与适配关系，不要求每个概念都有独立文件。

| 对象 | 含义 |
| --- | --- |
| Baseline | 外部规范及其固定版本，保存原始规范语义 |
| Profile | 选择适用要求、能力映射和证据要求的版本化适配；例外必须明确记录 |
| Project Instance | 某个仓库实际采用的 Profile 版本、检查入口和项目差异 |
| Adapter | 与 GitHub、执行器或平台交互，采集事实和提交已获授权请求的实现 |

Profile 的出现不会赋予权限，也不等于已部署 Ruleset。Adapter 不能用自己的 PASS 结果冒充仓库必需检查或授权。

| 原规范位置 | 采用语义 | Daedalus 的责任 |
| --- | --- | --- |
| §2、§15 | `main` 是仓库集成事实；PR 是语义内聚的原子变更 | 将 Capability / Task 关联到 PR 与实际集成提交 |
| §25 | 验证逻辑由仓库维护，本地与 CI 复用入口 | 解析入口、选择运行时机与环境、记录结果，不集中复制构建测试逻辑 |
| §26–27 | CI 生成权威仓库验证证据；Ruleset 执行合流准入 | 核对检查对象与可信生产者，观察门禁状态，通过既有工作流请求集成 |
| §2 Law 8、§30–31 | Fail-closed，只有明确定义的跳过可被接受 | 缺失、未知、取消、超时或检查错误不视为通过；跳过须有适用规则与理由 |
| §18、§21–23、§32 | 语义审查、审查时效与策略面保护 | 暴露需判断的事项，识别规则变化，不让候选变更自行降低当前门禁 |
| §29、§37–41 | 仓库工作流负责合流排序与准入 | 协调业务依赖，不另建与仓库 Merge Queue 竞争的合并排序器 |

| §44–45、§52 | 仓库负责发布流程和 Agent 变更准入 | 关联发布及制品事实，在更高层评估能力是否完成 |

`main` 的权威范围是某个仓库的集成状态，不是任务意图、生产运行情况或能力验收的统一事实源。

原文的“CI 是唯一权威验证证据生产系统”在此解释为仓库合流门禁的权威来源。Daedalus 还可以使用本地实验、平台验证、部署后观测和人工判断支持能力验收，但须标注证据种类与适用范围，不能把它们冒充该仓库的 Required Check。

## 项目接入需解析的信息

1. 仓库稳定标识、集成分支、目标基线和外部工作项关联。
2. 适用契约、Profile 与 Policy 的固定版本、权威来源及项目例外。
3. 仓库声明的验证入口、工作目录、环境要求、适用条件、输出位置及成功判据。
4. 必需检查的实际标识、可信生产者、事件与验证对象；名称只是关联线索，不能单独建立信任。
5. 实际审查与 Ruleset 配置、策略文件范围、合并方式，以及自动化身份的权限。
6. 能力验收所需的集成版本、制品或部署对象、使用路径与验收责任。

`task quality:fast`、`task quality`、`task quality:heavy` 是来源文档的接口示例。已有仓库可以暴露自己的权威入口；若不采用原文具体约定，应在 Instance 中记录适配或例外，不能默默宣称完全一致。

接入结果需要区分“文档要求”“平台实际配置”“当前运行事实”。仅检测到 CI 文件或本地检查成功，不能证明远端保护规则已启用。平台能力、检查名称、事件和权限需在实施接入时依据实际仓库核验。

## 接入前的待落实项

外部基线的可移植获取方式、首个消费项目、可信 CI 来源和能力验收入口需要在实施时确定。质量入口、CODEOWNERS、Ruleset 与实际权限配置要通过仓库检查取得事实；设计文档和首次公开同步都不能代替这些证据。

原规范中的全局 Git 配置、清理、推送、合并及发布命令均为参考内容，不能仅因本文引用该文档而自动执行。
