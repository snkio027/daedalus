## 仓库结构与开发环境

项目设计保留六个入口：`README.md`、`AGENTS.md`、`docs/product.md`、`docs/architecture.md`、`docs/engineering.md`、`docs/adr/README.md`。`docs/standards/README.md` 索引集中维护的公共工程规范及其固定版本，服务跨项目复用。ADR 在发生重要取舍时增加；协议文档和 Schema 在出现稳定接口消费者时再拆分。

文档使用 UTF-8 Markdown、相对内部链接和 Mermaid 概念图。当前没有应用源码、指定的产品实现语言或工具链，也没有应用构建、测试与运行命令。`scripts/check-docs` 是 Python 3 标准库编写的本地文档维护工具，`tests/test_docs.py` 验证其正常与失败行为；它们不决定控制面的实现技术。语言、依赖和生成代码策略由首个实现切片的需求决定；选择时记录理由，固定必要版本，并明确生成源和更新入口。

## Architecture v0 Design Review

架构设计通过以下三个 Gate 组织审查，关注反例、矛盾、空洞和过早抽象。Gate 是推进所需的评估与决策，不是新增三个静态状态文件；结果绑定被审查的提交，记录在 PR / 任务中。

| Gate | 必须审查 | 通过所需结果 |
| --- | --- | --- |
| G0 — Product Contract | 使命、四维质量、三循环、Capability、范围、自治与效果指标 | 产品契约足以指导设计，第一切片没有替代终态 |
| G1 — Domain & Control Model | 系统边界、ID / revision / 不可变记录、Event / Fact / State、Attempt 连续性、Change Revision、Authority、Evidence applicability、外部副作用、恢复及运行反馈 | 对具体场景和反例得到一致解释，关键未决项有明确处理，模型可作为 G2 输入 |
| G2 — First Vertical Slice Binding | 真实消费项目与能力、执行器、Workflow、环境、最小持久化、source / revision / digest、验收与反馈窗口、预算 | 每一项系统责任有实际承担者和可验证接口，形成可执行切片契约 |

G1 审查至少走查架构中的版本改变与运行任务处置、退出码为 0 但产出缺失、断连与写入所有权不明、进程死亡、未知副作用、证据的信任 / 完整性 / 覆盖差异、相矛盾证据，以及契约观察窗口和运行退化案例。G2 选择最少必要技术，不提前绑定语言、数据库、守护进程或 UI。

每个 Gate 的结论包含基线、覆盖、阻塞项、取舍、判断依据和接受责任；文档齐全或格式通过不能自动令 Gate 通过。确有需要时可以做有边界的验证原型，但应先明确实验问题与范围，不把它视为正式切片实现已获放行。

在合理替代方案、权衡与接受依据明确后再创建 ADR；不批量生成 Accepted 记录。任何尚未完成的设计审查都保持为未完成，不能从“已提交 PR”推定架构 Baseline 已被接受。

## 文档阶段的验证

每次文档修改检查：本地链接及锚点、代码围栏、尾随空白、文件末尾换行，以及术语、对象关系和职责是否一致。新增且未跟踪的文件也必须纳入检查，不能只运行忽略它们的 `git diff --check`。

在仓库根目录执行（需 Python 3.10+ 和 Git）：

```bash
./scripts/check-docs
python3 -B -m unittest discover -s tests -p 'test_docs.py'
git diff --check
git diff --cached --check
```

检查器读取 Git 跟踪及未忽略的未跟踪 Markdown，检查本地内联 / 引用式链接与标题锚点、围栏、管道表格列数、UTF-8 / 换行 / 尾随空白、Frozen 文件摘要，以及工作流迁移锚点。摘要表中的候选全文摘要也须匹配文件。缺文件、无效输入或检查错误返回非零；代码示例中的链接不当作导航。被忽略的文件不属于这份清单，准备交付的文件不能藏在 ignored 内容中。

范围限于本仓库采用的 Markdown 写法（ATX 标题、管道表格、内联链接及有定义的引用式链接），不是完整 CommonMark 渲染器；不联网验证外部 URL，也不验证平台事件、权限或 CI。无链接定义的方括号引文按普通文本处理，文献对应关系仍需人工核对。更改检查器时运行上述失败场景测试。普通文档修改运行检查器并做语义审查即可；Frozen 摘要只是字节一致性约束，不证明来源信任。

对已有基线的工作分支，确认实际集成基线后检查整个变更，例如 `git diff --check origin/main...HEAD`；提交前同时检查暂存区。初次提交没有父版本时，逐文件检查完整内容，再检查实际暂存集合。

架构审查按产品目标、架构驱动因素、系统上下文、领域模型、生命周期、信任与失败边界、合理替代方案和不变量推进。链接与格式通过不等于架构验收。验证报告留在本次任务或 PR 中，不复制为静态的“已通过”架构段落。

本仓库自身逐步使用相同体系：以文档设计能力为当前交付对象，明确契约、进行反例走查、保留检查与评审依据，再决定接受。它验证文档协作流程，不能代替真实功能、故障定位、跨平台及恢复案例对整个系统的验收。

当前只有上述本地文档检查及其测试，没有应用 `task quality` 或线上 CI。本地维护检查不构成 Required Check、规范采用决定或 G2 通过。引入首个产品可执行能力时，另行建立仓库自有验证入口，供本地与 CI 调用，并覆盖架构中的失败与恢复场景；命令成功、退出状态、日志和受测版本应可关联。性能实验需要固定输入、环境、正确性基线与测量方法。

未来持久化格式或外部接口发生兼容性变化时，应说明迁移与恢复方式。工具或依赖升级需运行受影响的代表性验证。上述约定不预先指定实现技术，也不声称当前具有这些检查设施。

## 初始化与后续交付

首次创建空远端时，在用户授权下将已检查的文档作为 bootstrap 提交建立 `main`。这一步建立初始基线，不视作已经完成 CI、Ruleset 或架构审查的证明。后续变更采用短期分支和 PR；保护规则、必需检查与审查身份需要独立落实和验证。

公开同步仅包含项目文档和后续明确纳入的工程资产。私人会话、机器绝对路径、凭据和临时执行记录不属于公共文档依赖。远端地址、提交与运行状态以 Git / GitHub 实际事实为准。

本仓库按已采用的 Git/GitHub v1.1 组织交付：短期分支、语义内聚提交、Draft PR、自审与明确证据。按其默认建议，集成接入目标选择 **PR-full + standard**；这是待落实的本仓库 Profile 目标，不是已通过平台接入验收的声明。当前本地文档检查不具有 Fast / Full Required Check 身份；线上检查、保护与审查条件尚须独立接入并实际验证。提交供审不需要伪造这些结果，合并前则必须核对实际准入与适用限制，不用本地通过或 Draft 可合并性代替。

## 接入前的待落实项

[云原生软件供应链安全工程指南](standards/software-supply-chain-security/2026-edition-draft.md) 是 2026-10-25 整理的 Proposed 专题，补充制品来源、构建证据、签名身份和部署准入；不属于 Architecture v0 或 Git/GitHub v1.1 的既有接受决定。消费项目可按实际交付对象评审并固定采用范围；本次收录不改变验证入口、集成路径、保证等级、发布权限或能力验收要求，也不启动 G2、修改 CI / Ruleset 或部署安全控制。

共享规范已有仓库内分发路径；实施时仍须绑定固定提交并验证消费环境可取得内容，确定首个消费项目、可信 CI 来源和能力验收入口。质量入口、CODEOWNERS、Ruleset 与实际权限配置要通过仓库检查取得事实；设计文档和公开同步都不能代替这些证据。

原规范中的全局 Git 配置、清理、推送、合并及发布命令均为参考内容，不能仅因本文引用该文档而自动执行。
