# 架构决策记录

ADR 记录具有长期影响、存在合理替代方案的架构取舍及其依据。日常实现选择、任务进度、PR 状态和验证日志保留在对应任务或运行记录中。

决策应说明对完整工程系统目标、四维质量和三循环的影响；局部实现便利不能隐式取代产品契约。核心指南落点及 G0 / G1 / G2 审查规则见 [engineering.md](../engineering.md)。

## 何时创建

当变更影响核心领域边界、持久化与兼容性、信任边界、外部依赖策略或主要执行机制时，评估是否需要 ADR。普通说明修订直接更新所属文档，不为每个改动创建决策文件。

## 内容与命名

文件名采用 `NNNN-short-decision-title.md`，编号递增。正文包含：标题、状态、背景与驱动因素、候选方案、选择及理由、后果与限制、相关验证或待验证假设，以及所影响的契约。

状态使用 `Proposed`、`Accepted`、`Rejected` 或 `Superseded`。接受决定需有明确评审依据；新 ADR 替代旧决定时双向关联并保留历史。发布草案或执行 `git commit` 本身不代表接受决定。

## 与架构正文的关系

[architecture.md](../architecture.md) 描述系统模型和不变量，ADR 解释为什么作出重要取舍；接受或替代决定时同步维护架构正文。避免在两个位置长期维护冲突的当前设计。

在具体取舍进入评审时创建首份 ADR，不预填一组未经讨论的 Accepted 决策。
