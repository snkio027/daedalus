### 后续资产的投入条件

| 触发条件 | 应产生的最小资产 | 责任与完成判据 |
| --- | --- | --- |

| 首个切片完成 | 问题→能力→设计→任务→执行→证据→交付→接受→反馈的完整案例 | 消费项目保存原始记录，Daedalus 维护者整理公开引用；示意与事实分开 |
| 复杂缺陷、容量或迁移问题出现 | 针对实际对象的诊断、性能、工具链或演进方法 | 对应责任人；解决明确问题并说明测量、失败和维护边界 |

这些是规划与完成判据，不是全部里程碑的执行授权。需求、设计、验证的方法优先在同一真实任务中校准；通用知识先寻找可固定引用的既有来源，再决定补写范围。

## 消费项目怎样采用

1. 先选择适用的内容和章节，区分规范、候选方法与专题建议；记录采用责任和例外，不直接复制 Daedalus 自身的 `AGENTS.md`。
2. 用来源仓库、完整提交、路径与 SHA-256 固定对象，由消费环境实际取得并校验。相对链接服务阅读，main/latest 不构成固定依赖。
3. 在消费项目自己的工程说明记录 Profile / Instance、权威检查入口、环境、权限、交付与验收责任；短入口只导航到这些依据。
4. 通过消费项目评审决定采用及迁移范围，再按真实任务核对接入、平台配置与结果。版本升级不自动授予线上变更或发布权限；未验证项保持未知。

这是采用信息的最低入口，不是已经实测的安装手册。[消费接入与 G2 准备方案](../plans/consumer-adoption-g2.md) 保存真实候选任务、实验选项和待决绑定，保持 Proposed；首次消费者完成后再沉淀可复现的采用示例。

## Baseline、Profile、Instance 与 Adapter

共享 Core 表达跨项目的领域、证据和授权语义；Baseline 是选用规范的固定来源。Core / Profile / Instance 是语义复用与适配关系，不要求每个概念都有独立文件。

| 对象 | 含义 |
| --- | --- |
| Baseline | 选用规范及其固定版本，不论来源为本仓库或其他知识源，均保存原始规范语义 |
| Profile | 选择适用要求、能力映射和证据要求的版本化适配；例外必须明确记录 |
| Project Instance | 某个仓库实际采用的 Profile 版本、检查入口和项目差异 |
| Adapter | 与 GitHub、执行器或平台交互，采集事实和提交已获授权请求的实现 |

Profile 的出现不会赋予权限，也不等于已部署 Ruleset。Adapter 不能用自己的 PASS 结果冒充仓库必需检查或授权。

## 项目接入需解析的信息

1. 仓库稳定标识、集成分支、目标基线和外部工作项关联。
2. 适用契约、Profile 与 Policy 的固定版本、权威来源及项目例外；分别绑定集成路径、保证等级、policy epoch 与验证器 revision。
3. 仓库声明的验证入口、工作目录、环境要求、适用条件、输出位置及成功判据。
4. 必需检查的实际标识、可信生产者、事件与验证对象；名称只是关联线索，不能单独建立信任。
5. 实际审查与 Ruleset 配置、策略文件范围、合并方式，以及自动化身份的权限。
6. 能力验收所需的集成版本、制品或部署对象、使用路径与验收责任。

v1.1 §25 的接口分为 Fast、Plan、Affected、Full 与 Extended；`quality:fast`、`quality:plan`、`quality:full` 等名称是接口示例，不要求引入特定任务工具。PR-full 使用 Plan → Full，不要求实现未使用的 Affected 入口；Queue 按计划执行 Affected，必要时升级为一次 Full。兼容入口 `task quality` 应保持 Full 语义，已有 `quality:heavy` 迁移前核对覆盖。已有仓库可以暴露自己的权威入口；适配或例外在 Instance 中记录，不能默默宣称完全一致。

接入结果需要区分“文档要求”“平台实际配置”“当前运行事实”。仅检测到 CI 文件或本地检查成功，不能证明远端保护规则已启用。平台能力、检查名称、事件和权限需在实施接入时依据实际仓库核验。

## 维护、勘误与版本演进

以下是本轮新增的 **Proposed 维护办法**，供评审；现有 Frozen 原文不变、固定来源和消费者显式采用要求继续有效。新方法或维护办法合入仓库不自动成为消费项目的已采用契约。

Daedalus 项目维护者负责目录、来源身份与内容变更评审；每个内容 PR 指明维护责任、受影响条款和依据。外部源作者维护原文，Daedalus 只维护固定引用与适配；消费项目维护者决定本项目是否采用、迁移及验证。角色改变或委托需能定位依据，不因代写文档取得批准权。

| 变更情形 | 处理与应记录内容 | 消费者影响与证据 |
| --- | --- | --- |
| 发现错误或歧义 | 在 Issue／PR 记录来源、完整 revision、路径、digest、条款、反例、严重性、责任和处置 | 说明可能受影响的行为、声明及历史结论；未解决的关键歧义不能被摘要掩盖 |
| Frozen 正文需要纠正 | 保持旧文件字节和路径；索引关联勘误记录，技术修订发布新版本并引用旧身份 | 区分解释、替代与不兼容变更；勘误不静默改变已采用字节或权威语义 |
| 候选方法迭代 | 增加修订号与变更记录，更新完整文件摘要，保留旧提交 | Proposed 不因审查或本地检查变成 Adopted；试验仍固定实际修订 |
| 新版本或适配器发布 | 列出语义差异、规范／方法／工具的已验证组合、未测组合和迁移／恢复步骤 | 文件名或版本号不证明兼容；验证结论仅适用于声明范围 |
| 弃用、撤回或升级 | 记录决定主体、日期、原因、替代物、期限及是否限制新采用；保留历史 | 枚举已知消费者、采用记录、继续旧版的理由／风险和待核对项目；未知消费者明确未知 |
| 外部源失效、工具升级或关键假设变化 | 核对固定副本、访问和摘要，评估加载、权限、验证与证据适用性 | 身份可信的固定副本可按既有契约使用；缺必需依据或已知错误受影响时阻塞相应判断，不回退 latest |

变化影响运行中工作时，采用版本升级不静默改绑 Task / Attempt；沿用架构的继续、取消或显式迁移，并保留旧证据和未决副作用。升级不自动撤销全部历史证据，也不保留已知不再适用的绿灯；逐项说明失效范围与复验责任。

同一 Instance 分别记录规则版本、方法版本、分发包／Skill／Plugin 版本、执行器及工具版本、实际配置与采用决定。工具可加载新规则不等于项目已批准升级。退出采用时明确替代的质量与授权责任、依赖该规则的自动化、历史证据保留及验证；移除入口文件不证明旧控制已替代或在途操作已停止。

影响分析与结果留在关联 Issue／PR／消费项目记录，目录只保留稳定入口。方法改进先在代表性任务上记录成功、失败、遗漏、人工投入和总成本，再由有权责任人决定采用或回退；不新建没有消费者的注册中心。完成判据是能够说明哪些已知项目受影响、哪些继续旧版，以及决定和证据在哪里。
