`TransformRun` 是数据平台的一次处理尝试，可能是某个 Daedalus Attempt 调用的外部运行，也可能来自独立调度器。通过平台命名空间、Task / Capability revision、Attempt 和运行 ID 记录关系，不假定一一对应。数据平台运行结束不自动终结 Daedalus Attempt；后者仍按 Architecture v0 §7 的执行连续性与输入绑定判断。

`accepted` 请求接纳、`published` 数据发布、`AcceptedView` 用途视图与 Capability Acceptance 各有对象和判据。发布状态提交只确认发布契约，使用路径及必需观察仍由 Capability 契约决定；后续 Evaluation 独立继续。既有 Task 不随 Capability 或数据契约的当前版本自动迁移，沿用架构的继续、取消或显式迁移决定。

本指南的 `ReadPlan` / `ConsumptionPlan` 是数据访问和消费契约，不是 Git/GitHub 的 `quality:plan`。第 13 章 `DM-G01` 至 `DM-G12` 是数据平台验收项，M0–M3 是消费项目建设里程碑；两者均不替代或放行 Daedalus G0 / G1 / G2。Architecture v0 的 G0/G1 接受状态不扩展到本文，G2 仍未启动。

`PR-full / Queue` 与 `standard / assured` 继续独立选择。standard 依赖可信责任人及审查；assured 未完成独立核验接入时保持阻塞。新的数据检查由仓库映射到已有入口；必需 Plan 缺失或失败不能用数据发布成功掩盖，本地未进入计划路径的 Full 仍按 v1.1 运行。签名、血缘或一次数据检查通过不构成保证等级升级。

读取计划中的 `policy_epoch` 标识其数据授权策略域，不与仓库 Quality context 的 epoch 共用含义。数据质量、使用策略与验证器分别版本化；何时使旧判断失效取决于原结论是否仍可接受，不要求每次验证器修改都迁移仓库门禁。会降低接受条件的规则变更按已有权威审查，候选不能自行降低自己的门禁。

本指南的采用、数据平台实现、运行验收分别记录。收录与导航不代表已采用，也不授权提交推送、CI / Ruleset 修改、资源采购或生产动作；技术骨架与仓库目录仅供消费项目选择。既有 elliott.page 试点及其比较基线保持原范围。

## 执行摘要

本设计的目标不是建设一个包办所有数据的数据库，也不是用知识图谱、向量或 Context Layer 替代传统数据建模。目标是建立一套统一的引用、解释、交付与治理契约，使同一份数据能够服务分析、模型学习、检索和 Agent，并在持续变化中保持可解释、可验证与可演化。

总体采用“共享底座、三类模型、四个平面”。共享底座提供身份、版本、时间、契约、来源与使用策略；三类模型分别表达领域与证据、学习数据、运行与反馈；数据面、控制面、管理面和证据面分别承担实际内容、状态协调、规则治理与执行记录。它们是职责边界，不是必须独立部署的微服务。

物理层采用多种互补形态：对象存储承载原生载荷与制品；开放表承载批量记录与快照；事务数据库承载低基数、强事务的控制状态；专用索引承载在线访问；训练布局承载高吞吐消费。统一的是身份、版本、权限和证据，不是强制统一格式、存储或协议。

平台的核心交付接口由三个对象组成：**DatasetRelease 固定逻辑内容，DeliveryLayout 固定物理交付，ConsumptionPlan 固定实际消费行为。** 一个数据集可以有多种布局，但内容转换、分词、监督掩码和采样变化必须显式登记，不能伪装成无影响的“重新打包”。

当前建设阶段应以一个真实来源、一个主要模态、一个明确消费任务完成纵向闭环：可靠接纳 → 版本化处理 → 质量与用途检查 → 固定发布 → 真实消费验证。知识图谱、向量检索和 Agent 接口由实际任务触发，不作为一期完整性的前提。

**本版最重要的验收标准：从任意已发布样本，能够说明它来自哪里、具体是哪一版、经过什么处理、为什么入选、当前允许怎样使用，以及怎样重新读取。** 数据读取可重建，不自动意味着模型训练数值结果逐位一致；服务部署成功，也不等于数据产品已经通过验收。

## 1. 定位、范围与设计原则

### 1.1 AI-native 的工程定义

本文把 AI-native 数据建模定义为：面向 AI 学习与运行，把数据内容、解释契约、监督与采样、证据、用途条件和反馈结果共同纳入模型；让数据可寻址、可组合、可追踪、可评测，并具有明确的失效和撤回语义。

AI 不取消主键、关系基数、事务、时间和 Schema 演化。来源建模也不是 AI 时代才出现的新概念：W3C PROV-DM 已通过实体、活动和主体描述来源关系。[R01] 本设计是在这些基础上扩大责任范围，而不是宣告表、SQL 或关系模型过时。

本文不把“统一语义”解释为全局唯一的领域本体。各领域可以保留自己的模型，通过受治理的映射和版本化契约协作。AI 生成的摘要、标签和关系是有产生过程的输出，不因进入数据库就升级为可信事实。

### 1.2 范围与非目标

范围覆盖结构化记录、事件、文档、代码、图像、音频和视频；覆盖资产登记、处理、发布、查询、传输、训练输入、检索上下文及生命周期治理。

本版不提供具体集群安装清单，不预设用户现网组件和容量，不承诺跨系统全局事务、无限历史保留、即时收回所有外部副本，或通过删除数据自动消除已训练模型中的影响。具体组件版本、可用性目标和吞吐门槛须通过后续兼容性与负载验证确定。

### 1.3 核心设计不变量

| 编号 | 不变量 | 设计含义 |
| --- | --- | --- |
| INV-01 | 身份不依赖位置 | 迁移、分片与文件合并不改变逻辑资产或样本身份 |
| INV-02 | 解释绑定版本 | 内容引用、Schema、语义和处理规则必须可以固定到明确版本 |
| INV-03 | 正式发布不可静默改写 | 内容修订产生新发布；是否允许使用由独立状态控制 |
| INV-04 | 派生结果可追踪 | 已发布输出能够定位输入、运行、代码／模型和配置 |
| INV-05 | 权威状态唯一且有边界 | 搜索目录、缓存和索引不得替代提交或授权权威 |
| INV-06 | 授权覆盖实际读取粒度 | 对象直读不能绕过行级、列级或用途限制 |
| INV-07 | 失败不能暴露半成品 | 只有通过发布契约的结果才对正式消费者可见 |
| INV-08 | 重试不产生无意重复结果 | 稳定幂等键、唯一约束、提交协调和对账共同保证 |
| INV-09 | 引用保留与清理协调 | 有效发布、运行与读取租约的依赖不能被普通清理误删 |
| INV-10 | 学习行为显式可追踪 | 采样、模板、分词、监督与恢复状态不能隐藏在未登记脚本中 |
| INV-11 | 资源有界 | 在途字节、解码内存、并发、缓存和队列都有上限 |
| INV-12 | 证据不冒充结论 | 可追溯不等于真实，读取成功不等于训练有效，模拟测试不等于生产验收 |

这些是不变量目标，不是本版已经通过的测试结果。第 13 章给出验证方法和证据要求。

## 2. 总体结构：多维组织，而非一棵万能目录树

### 2.1 六个组织维度

| 维度 | 回答的问题 | 主要单位 |
| --- | --- | --- |
| 业务与语义 | 代表什么，由谁负责？ | Domain、Concept、Entity、DataProduct |
| 身份与版本 | 哪个对象、哪个状态、哪个部分？ | Asset、Revision、ContentUnit |
| 存储 | 字节怎样持久化、分区、压缩与复制？ | Object、Table、File、Partition、Shard |
| 查询 | 怎样发现、筛选、关联和读取？ | Catalog、View、Projection、ReadPlan |
| 传输 | 怎样可靠移动内容和状态变化？ | Event、RecordBatch、Stream、Transfer |
| 管理与证据 | 怎样授权、发布、追踪和撤回？ | Contract、Policy、Release、Run、Assessment |

一个业务领域、一个对象存储前缀、一个 Kafka 分区、一个训练分片和一个训练 batch 属于不同维度。文件边界不能定义样本身份；消息分区不能定义永久业务归属；梯度更新的 batch 不能定义数据集版本。

### 2.2 共享底座与三类模型

**领域与证据模型**表达实体、事件、观测、声明、概念、关系、来源和证据。它回答“这是什么，以及我们依据什么知道”。

**学习数据模型**表达样本、目标、标注、偏好、轨迹、奖励、配方、混合分布、切分和评测。它回答“怎样把数据转化为学习信号”。

**运行与反馈模型**表达任务、上下文、检索、工具调用、授权动作、执行结果和评价。它回答“系统实际使用了什么、做了什么，以及结果是否满足目标”。

三类模型共享引用、时间、版本和策略，但不强制塞入一个万能 DataObject。文档描述实体、图片描绘实体、摘要派生自文档，与关系记录和 JSON 对同一内容的等价编码，是不同关系。

### 2.3 四个平面与典型链路

| 平面 | 主要职责 | 典型对象 |
| --- | --- | --- |
| 数据面 | 内容持久化、读取、解码、交换与处理 | 原生载荷、湖表、分片、索引、缓存 |
| 控制面 | 提交、任务、发布、读计划和租约协调 | Run、PublishIntent、ReleaseStatus、ReadPlan |
| 管理面 | 责任、语义、契约、用途与生命周期规则 | Owner、Contract、Policy、RetentionRule |
| 证据面 | 来源、质量、访问、成本与执行记录 | Lineage、Assessment、Audit、Receipt |

主链路如下。分支中的模型是对同一底座的不同使用方式，而非互斥的数据仓库。

```text
Sources -> Native Revisions -> Content Units -> Transform / Assess
                                           -> Learning Examples
                                           -> Semantic / Search Projections
                                           -> Evidence and Relations

Build + Validate -> DatasetRelease -> DeliveryLayout -> ConsumptionPlan
                                      |                    |
                                Query / Retrieval     Train / Evaluate
                                      +------ Feedback -----+
```

管理规则约束所有路径；证据随执行产生；控制面不应代理全部数据流量。独立部署只在权限、伸缩或故障隔离需要时引入。

## 3. 核心逻辑模型与引用契约

### 3.1 身份、版本、内容与位置

建议采用三层公共引用。字段组合的编码可以由 API 契约确定，不把示例字符串当成通用 URI 标准。

```text
AssetRef    = authority_namespace + asset_id
RevisionRef = AssetRef + revision_id
ContentRef  = RevisionRef + selector
```

`authority_namespace` 是稳定身份管理空间，不是可随组织调整变化的团队路径。`revision_id` 是不透明版本标识，不默认具有时间或大小顺序。需要顺序时显式使用来源版本、提交序号或 epoch。

`content_digest` 校验指定字节表示，不自动成为业务身份；`storage_ref` 定位物理副本，不决定其语义；`schema_ref` 解释结构，不替代字段单位、记录粒度和用途说明。摘要必须记录算法与计算范围，不能默认把对象存储的 ETag 当成全内容加密哈希。

相同字节可以来自不同来源并具有不同使用条件。跨租户去重需要评估内容存在性泄漏、密钥和删除边界；默认在明确的安全域内复用字节，分别保留来源与权利记录。

### 3.2 最小核心对象

| 对象 | 记录粒度与必需关系 | 默认承载位置 |
| --- | --- | --- |
| SourceRegistration | 一个来源及其身份、接入和用途契约 | 控制数据库 |
| Asset / ArtifactRevision | 一个资产及其具体内容版本 | 登记索引＋对象／湖表 |
| ContentUnit | 某个版本中的一个类型化内容单元 | 领域湖表 |
| TransformRun | 一次处理尝试的输入、配置、输出和结果 | 运行登记＋明细制品 |
| Annotation / Assessment | 针对明确版本目标的一次标注或评价 | 湖表；必要时在线索引 |
| TrainingExample | 按任务契约定义的样本版本 | 样本表／制品 |
| DatasetRelease / DatasetMember | 一次固定发布及其精确成员 | 发布登记＋清单／成员表 |
| DeliveryLayout | 一次发布的物理交付组织 | 布局登记＋分片清单 |
| ConsumptionPlan | 一次消费的固定输入与行为配置 | 计划制品＋运行引用 |
| ServingProjection | 某种服务索引或物化视图的版本 | 投影登记＋专用存储 |
| ContextManifest | 某次任务实际纳入上下文的内容与工具结果 | 审计制品 |

以上是逻辑对象，不要求“一种对象一个服务”，也不要求为每个观测值在 PostgreSQL 创建对象行。高基数内容用表、批次与分层清单表达；控制数据库只保存需要强事务的登记状态及必要索引。

### 3.3 类型化内容定位

| 内容类型 | Selector 必须明确的内容 |
| --- | --- |
| 文本／文档 | 结构节点或区间；偏移单位；解析版本；必要的原始页面映射 |
| 图像 | 目标图像版本；尺寸；坐标原点；区域／掩码编码 |
| 音频 | 时间基准；起止区间；声道；重采样或裁剪版本 |
| 视频 | 时间基准；轨道；时间区间；必要的空间区域与帧映射 |
| 结构化记录 | 稳定记录标识与版本；必要的字段标识；不能只引用文件内行号 |
| 代码 | 仓库版本；文件／符号；文本区间及编码 |

多模态对齐是独立的版本化关系。字幕、音频和画面不能靠数组下标“碰巧相同”关联。重采样、裁剪或解析变化可能使旧 selector 失效，应生成新单元或显式坐标映射，不能原地复用。

### 3.4 时间与可知性

| 时间语义 | 定义 | 注意事项 |
| --- | --- | --- |
| event_time | 事件发生时间 | 可能迟到、乱序或来自不可信时钟 |
| observed_at | 来源或系统观察到内容的时间 | 不一定等于事件发生时间 |
| valid_time | 业务事实或规则适用的时间区间 | 区间边界、时区和开放端点必须定义 |
| recorded_at | 平台记录该版本的时间 | 用于说明“平台何时知道”，不是绝对真相 |
| committed_at / published_at | 数据提交／正式交付时间 | 提交、批准与对外可用要分开 |

不要求所有对象拥有全部时间字段。需要历史纠错或“当时已知信息”评测时，明确区分有效时间与记录时间；时间戳本身不证明跨系统因果顺序。来源缺失或时钟不可信应保留状态，而不是伪造精确时间。

### 3.5 声明、证据和不确定性

Observation 是某个观察过程的结果；Assertion 是某个主体提出的声明；Evidence 是可定位的支持或反驳材料；Assessment 是按特定准则产生的评价；AcceptedView 是在明确规则下供某种用途使用的视图。

“被系统接受”不等于“现实中必然为真”。置信度必须说明评分对象、方法、量纲与校准依据。模型自评分、分类分数和人工可信度不能不加说明地合成一个通用 confidence。证据与声明之间还要验证支持关系，而不只是检查引用能否打开。

用于工程或能力判断的材料按 Architecture v0 §8 分别记录 producer trust、evidence integrity、semantic coverage、actual result，以及 `applicable(E, DecisionContext)` 的 true / false / unknown。前三项各有满足、不满足或未知及依据；它们不能合并为一个可信布尔值。可信且适用的失败证据可以支持拒绝，血缘完整、摘要或签名正确均不自动支持通过。必需命题来自已接受契约；适用失败与冲突未处置时，不能只挑一次绿色重跑。数据 Assessment 作为评价记录引用原始证据，不把评价者的结论当作独立运行事实。

必需证据集合由已接受的产品契约和策略确定，候选上传的 evidence_manifest 只是实得材料，不能自行删减必需项。核对实际生产者、运行、受测内容及受保护的验证定义；受信任服务仅为候选自填的来源或 PASS 签名，不能建立该声明的可信生产链。按已选保证等级落实责任，不把人工核对描述为机器强制保证。

冻结清单保存当时的证据引用，不封闭未来的证据集合。更正、撤销、新失败和处置决定以关联记录追加；每次正式判断都要核对当前决策上下文中的有效记录，不能只读发布时的绿色集合。复用评价或验证缓存须绑定对象、命题、证据身份、信任／策略／验证器版本、时效和撤销状态；摘要相同或 TTL 未到不单独构成复用依据。

## 4. 存储组织与物理布局

### 4.1 按职责分配存储

| 类别 | 主要内容 | 设计约束 |
| --- | --- | --- |
| 原生载荷 | 原始文档、媒体、代码包、原始采集批次 | 不静默覆盖；有摘要和来源；保留受策略约束 |
| 规范化记录 | 内容单元、业务记录、标注、质量和成员关系 | 明确粒度；可批量扫描；支持版本化读取 |
| 控制状态 | 来源、任务、发布、策略绑定、租约、Outbox | 强事务、唯一约束、幂等与审计 |
| 派生制品 | 摘要、模型标注、token 数据和转换输出 | 绑定输入和方法；必要时长期保留实际输出 |
| 服务索引 | 全文、向量、关系遍历和低延迟定位 | 声明覆盖范围、新鲜度、输入版本和重建方法 |
| 交付布局 | 训练分片、导出文件和固定读取索引 | 精确成员映射；不可变清单；校验与保留依赖 |
| 缓存 | 热数据、解码结果和预取内容 | 有界；受权限和撤回控制；不能成为唯一副本 |

Parquet 提供列式文件表示；Iceberg 在文件之上提供表元数据、快照与演化机制，二者不是同一层。[R02][R03] 本文把对象存储、开放表和控制数据库视为互补职责，而非竞争选项。

**派生不等于可丢弃。** 人工标注、昂贵生成结果和非确定性模型输出可能无法精确重建。只有在业务契约、重建成本和审计要求允许时，某个派生结果才可以仅作为缓存处理。

### 4.2 对象存储命名与安全域

以下为逻辑职责示例，不要求每个前缀对应一个独立桶。`cell` 表示区域、环境或安全隔离单元。

```text
<cell>-payload/sources/<source_id>/<asset_id>/<revision_id>/...
<cell>-lake/tables/<table_uuid>/...
<cell>-artifacts/runs/<run_id>/<artifact_id>/...
<cell>-releases/<dataset_id>/<release_id>/manifest.json
<cell>-delivery/<release_id>/<layout_id>/<shard_id>/...
```

S3 对象键空间是扁平的，前缀提供组织方式而不构成真正的目录语义。[R07] 路径服务运维、定位和生命周期，不能替代逻辑身份、责任归属或实际授权。敏感业务标识不应直接暴露在路径中。

表目录由表引擎管理，禁止绕过协议手工移动表文件。平台级稳定引用不意味着底层表的迁移可以任意改路径；迁移须遵循表格式与具体引擎能力，验证全部元数据和文件引用后切换。

原始对象建议采用条件写、唯一键或供应商提供的版本能力防止意外覆盖。AWS S3 有 If-None-Match／If-Match 条件写语义；其他兼容存储必须实测相应行为，包括并发与失败重试。[R08]

### 4.3 表、分区、排序与分片

表首先按记录粒度和生命周期划分，例如文档单元、媒体区间、标注、评价、样本、成员和派生关系。领域划分、权限、规模与访问要求决定是否拆表；不建设一张承载所有模态、全是可选字段的万能表。

分区用于减少扫描和管理生命周期；排序／聚簇改善局部读取；文件合并控制小文件成本；训练分片定义连续读取与并行分配；索引分片控制在线容量与负载。不能用一种分片方案替代全部问题。

Iceberg 支持 Schema、分区与排序演化，使逻辑契约与物理优化可以分离。[R04] 但具体字段类型、删除特性与读写引擎组合仍需测试。文件大小、行组大小和桶数由压缩后尺寸、请求成本、过滤模式与恢复开销确定，本版不指定无负载依据的“最佳值”。

### 4.4 热温冷分层与多副本

热层服务低延迟读取和训练预取；温层保留经常使用的对象与湖表；冷层用于长期保留。归档恢复需要时间的对象不能被宣称为立即可读的发布依赖，应在发布可用性与读取计划中表达恢复状态。

物理副本登记包括区域、安全域、摘要、复制状态和可用性。复制与备份不同：误删、错误提交和凭证泄漏需要独立恢复能力。密钥备份和保留关系同样重要；有密文字节却失去合法解密能力，仍是不可读取。

## 5. 查询与访问组织

### 5.1 统一发现与授权，多种执行路径

| 访问模式 | 典型用途 | 执行路径 |
| --- | --- | --- |
| 资产发现 | 查找可用来源、契约、产品和负责人 | 目录搜索与元数据查询 |
| 精确查询 | 筛选、关联、聚合、历史分析 | SQL 引擎、开放表和物化视图 |
| 内容读取 | 读取某个版本中的片段、区域或时间段 | 版本解析器、对象 API、必要的解码服务 |
| 相关性检索 | 找到与问题相关的内容 | 全文、向量或混合索引 |
| 关系与血缘 | 影响分析、追溯、依赖检查 | 关系表或专用图索引 |
| 批量消费 | 训练、评测、导出 | 发布清单、分片 Reader、预取缓存 |

平台不强迫所有请求转成 SQL，也不允许所有消费者绕过权限直连底层存储。Trino 的 Iceberg connector 提供表读取和快照／引用相关查询能力，可以复用成熟执行器；平台自身负责解析产品、版本、权限和消费范围。[R13]

### 5.2 读取模式与跨表一致性

`pinned` 读取指定发布或快照；`latest_committed` 在请求开始时解析当前已提交版本并固定本次读取；`bounded_staleness` 允许使用满足声明新鲜度要求的派生视图。

多个表分别取“某时刻之前最新快照”不自动形成业务一致截面。跨表产品须由发布器检查共同构建计划、来源进度和业务约束；流式构建需要显式输入 frontier，即各分区或来源的处理位置向量。事件时间 watermark 也不能自动证明没有遗漏。

索引登记应包括输入版本、构建运行、覆盖范围、连续处理位置、缺口与失败区间。不能只用“最近更新时间”或最大的已处理 offset 代表完整性；中间缺口必须可见。严格检索回放还需保留实际结果或相应索引制品，不能仅保存 embedding 模型名称。

### 5.3 ReadPlan：把控制决策与大规模读取分开

建议先完成发现、授权和版本选择，再生成读取计划，由消费者直接读取被授权的分片或受控结果流。

```text
ReadPlan {
  plan_id, principal_ref, purpose
  release_ref, layout_ref, schema_refs
  selected_scope, endpoint_manifest_ref
  policy_decision_ref, policy_epoch
  retention_lease_ref, expires_at
}
```

生成计划时登记必要的读取租约，防止读取过程中普通清理删除依赖。租约到期、授权变化和撤回规则必须可执行；读取租约不是绕过撤回的永久通行证。凭证与控制状态分开保存，不把签名 URL、令牌或密钥写入长期清单。

ReadPlan 固定解析后的对象与范围，`policy_decision_ref` 保存当时依据，不冻结未来授权。签发、续发凭证以及实际返回数据时，执行端须核对主体、用途、实际 release／layout／scope、当前发布与授权状态；消费计划恢复也经过此边界。缓存命中、切换端点或恢复检查点不得跳过检查。授权复用必须处于契约允许的有效窗口内，并能落实撤销；无法确认必需条件时停止继续暴露，不能回退到历史批准。

### 5.4 授权必须覆盖实际暴露的数据

只有消费者有权读取整个对象时，才能授予对象直读。如果 Parquet 或 tar 文件混合了无权访问的记录，应走受控过滤结果、独立授权导出或按安全边界拆分的布局。范围请求不能替代授权，因为持有对象凭证的一方可能请求其他范围。

S3 预签名 URL 是具有期限、依赖签发者权限的持有者凭证，并不自动执行平台的行级、列级或用途规则。[R09] 查询结果缓存、预览、统计信息和搜索摘要也需执行相同可见性规则，不能只保护原始载荷。

对向量／全文检索，可在受控边界中预过滤，或检索后再次授权并补足结果。无论采用哪种方案，未授权内容、引用与敏感统计都不得返回；权限变化还应推动投影和缓存失效。

消费项目须声明撤回传播时限、长流／预取的重新检查点、在途终止方式及执行责任，验证实际暴露窗口。短期凭证不自动满足这一要求：S3 在 HTTP 请求开始时检查预签名 URL 的到期时间，已开始的下载可在到期后继续。[R09] 若目标存储或客户端不能达到所需撤回边界，应选择受控读取路径或限制采用范围；不能宣称修改目录状态即可立即收回已发字节。

## 6. 传输、增量与处理协议

### 6.1 按载荷性质选择传输方式

| 路径 | 传输内容 | 建议形态 |
| --- | --- | --- |
| 控制调用 | 登记、状态、计划、授权 | HTTP／gRPC＋类型化消息 |
| 持久化事件 | 来源变化、记录变更、发布通知 | Kafka 或其他可回放日志 |
| 大对象 | 原始媒体、文档、训练分片 | 对象 API、并行／范围读取 |
| 计算交换 | 结构化批量数据 | Arrow RecordBatch／IPC／Flight |
| 同机交换 | 已解码缓冲区 | 显式所有权的共享内存或进程内缓冲区 |
| 训练输入 | 固定版本分片与预取块 | Reader、节点缓存与预算化预取 |

Arrow 定义列式内存表示与 IPC；Flight 提供基于 RecordBatch 的服务与多端点读取机制。[R10][R11] 它们可以降低逐行序列化成本，但不能保证网络、解压和设备传输全部零拷贝。已经在对象存储中的大文件无需为了接口统一而绕行集中式转发服务。

### 6.2 事件描述变化，引用定位大载荷

小型原生业务事件可以携带必要内容；大文件通过已提交引用传递。CloudEvents 适合统一事件信封，但不定义业务幂等、顺序或跨系统事务。[R12]

建议事件携带稳定的 `(source, event_id)`、事件类型、发生与记录时间、对象／版本引用、载荷 Schema、摘要、因果或提交信息。相同事件重复投递应复用身份，不能每次重试都生成新 ID。需要有序更新的聚合使用明确 sequence／epoch，不依赖 UUID 或跨主机时间戳排序。

对外发布“载荷已提交”事件前，内容必须已经可读取。日志回放期限、对象保留期限和最大重试窗口要协调，否则会出现消息仍在而内容已清理的悬空引用。

### 6.3 四个完成点与可靠提交

| 状态 | 含义 | 不代表什么 |
| --- | --- | --- |
| accepted | 请求已被接纳 | 不保证载荷已经持久化 |
| durable | 内容可靠持久化且可验证读取 | 不保证解析或质量检查通过 |
| processed | 指定处理已完成并登记结果 | 不保证可供正式消费者使用 |
| published | 已满足产品发布契约 | 不保证以后永远允许访问 |

原始接纳、下游处理与正式发布是不同状态机。ACK 的契约必须指向明确完成点；消息位置只有在必要的持久化效果成立后才能推进。顺序提交应依据连续完成前缀，而不是最大已完成位置。

对控制数据库中的变更，建议将权威状态与 Outbox 同事务提交，再异步转发事件。Debezium Outbox Event Router 是可复用实现，但消费者仍须处理重复与重试。[R15] Kafka 的事务能力不会自动覆盖对象存储、湖表和外部索引；外部输出与消费位置必须另外协调。[R14]

默认策略是允许至少一次交付，使用幂等键、唯一约束、提交检查和对账消除无意重复结果。外部有副作用的动作还需要动作级幂等或补偿协议，不能仅靠消息去重承诺“恰好一次”。

外部操作在发送前持久记录稳定 operation ID、目标、期望修订、请求语义与授权引用；事件 ID、幂等键和操作 ID 分别承担投递识别、目标接口去重和逻辑副作用关联。沿用 Architecture v0 §7.2 的 requested / sent / confirmed / failed / unknown。未知时核对目标权威状态、查询范围与完整性，阻止同一副作用和冲突目标的再次写入，限制跨 Attempt、Worker 和工作区生效。超时、一次未找到或进程死亡不证明请求没有发生或不会迟到。

确认未发生且原请求不会继续产生效果、授权仍有效后，才按接口契约重试；重试保留同一逻辑操作身份，并核对幂等键作用域、请求一致性和有效期。部分完成分别记录，改变目标或请求需新建关联操作，不能用新 ID 清空未知范围。取消须核对远端延后动作，回滚、删除孤儿和补偿各需相应授权。

恢复时先区分“已发生的效果”与“现在允许的动作”。例如发布已提交但响应丢失，随后授权撤销：核对确认的原操作仍记 confirmed，并保留提交与撤权时间、对象及审计依据；这不证明当时合规，也不恢复当前使用权。尚未发出的发布、分发或重试被现行策略阻止，撤回／取消／补偿另按相应权限处置。若证据显示发生的是不同对象或部分效果，分别记录偏差与未知范围，不能将其充作预期操作成功。

### 6.4 资源上界与取消

至少约束在途压缩字节、解码后字节、请求并发、CPU／GPU 解码任务、输出缓冲区和未提交制品。解压膨胀比和超大样本需要单独防护；不能只按消息条数限流。

交互查询、训练读取和后台重建使用独立预算，控制请求不得被批量载荷长期阻塞。关闭顺序应停止接纳、取消或收敛在途工作、提交可证明完成的结果，并保留可恢复状态。租约到期、失联或取消请求都不证明旧 Worker 已停止。只有确认旧写入者已停止，或其作用范围内的写能力已可靠撤销／隔离，并核对已有输出与在途操作后，才由唯一协调权威移交写入权；不能因超时直接启动第二写入者。

采用 fencing 时，受保护存储／提交端必须实际拒绝旧写入，并验证所有相关写入路径；在协调器内检查一次租约或在请求中附带 token 不构成隔离证明。只保护发布指针的 fencing 不等于已隔离共享工作区和对象写入。独立工作区也不解除同一发布目标的未知操作限制。

## 7. 发布、布局与消费计划

### 7.1 三个不同的冻结边界

| 对象 | 固定内容 | 变化后的处理 |
| --- | --- | --- |
| DatasetRelease | 精确样本版本、成员、切分、样本内容／目标含义、解释契约与构建证据 | 已发布逻辑内容或解释契约变化产生新发布 |
| DeliveryLayout | 所属发布、声明的覆盖范围、文件／分片／索引／编码、成员映射及适用输入规范 | 重排／重新压缩产生新布局；不能借布局变更改写逻辑内容 |
| ConsumptionPlan | 发布组合、选定范围与布局、采样、TrainingInputSpec、分配与恢复约定 | 消费行为或所选引用变化产生新计划或显式修订，不原地改绑旧运行 |

DatasetSnapshot 表示输入集合状态；DatasetRecipe 表示选择与构造方法；MixtureRecipe 表示混合与采样；TrainingInputSpec 表示训练输入生成方式。各对象固定其实际依赖：发布绑定构建逻辑内容所用的输入／配方，消费计划绑定消费时的混合／输入规范，不要求每份发布预先选定所有训练行为。

例如，修改已发布答案、成员或切分需要新 DatasetRelease；仅改变同一逻辑样本的运行时模板、tokenizer、loss mask 或采样，且未违反发布契约时，修订 ConsumptionPlan／TrainingInputSpec 即可。若发布本身交付 token、掩码或增强后样本作为逻辑内容，改变这些内容仍须新发布。判断依据是对象已经承诺的语义，不能通过改名为“计划参数”绕过发布不变性。

计划契约修订与运行进度分开。ConsumptionPlan 固定输入与行为配置；运行中的游标、随机状态和恢复快照作为关联的版本化运行记录保存，不原地改写已用计划。输入发布、训练输入规范或消费行为改变时，显式决定继续旧计划、停止或迁移，核对检查点兼容性及重复／遗漏边界；不能把旧运行静默改绑到新计划。若同时改变 Daedalus 的 Task revision、主要执行器配置或执行输入基线，按架构创建新 Attempt 并保留历史。

token 化、裁剪、增强、模板和 packing 可能改变学习信号。预计算交付制品须同时固定输入发布、TrainingInputSpec 版本、生成实现及内容摘要，说明其实现的是哪种消费行为。只有与计划要求相符且等价性有依据时，Reader 才能使用；不能把它们等同于无损布局转换，也不能在发现不兼容时静默回退另一份输入规范。

### 7.2 发布清单示例

下例是本文建议的契约草案，不是现成标准，也不是可直接部署的生产配置。ID 与快照均为占位示例；引用须通过受信任登记解析到固定版本和摘要，不能解析为 latest。最终清单摘要与准入决定由外部发布登记关联，避免清单与决定互相包含对方摘要。

```yaml
manifest_schema: dataset_release/v1
namespace: example
release_id: rel_007
dataset_id: maintenance_qa
contract_ref: {id: qa_contract, revision: c3}

membership_ref:
  kind: iceberg_snapshot
  table_id: dataset_members_maintenance
  snapshot_id: "4821"
  release_key: rel_007

example_schema_ref: {id: qa_example, revision: s4}
recipe_ref: {id: qa_recipe, revision: r12}
split_policy_ref: {id: source_group_split, revision: s2}
build_run_ref: {id: build_007, attempt: a1}
input_manifest_ref: input_manifest_007
evidence_manifest_ref: evidence_manifest_007
dependency_manifest_ref: dependency_manifest_007
```

先冻结清单字节并计算摘要，准入决定再绑定该摘要、发布对象、必需证据与策略版本；发布登记原子关联这一确定清单与决定。批准后替换清单须重新判断，不能只沿用相同 release_id 或旧决定。准入决定不写回被冻结清单，后续评价及撤回记录另行关联。

成员必须固定到记录／样本版本，不能只保存会变化的 SELECT 查询。大规模成员用表快照或分层清单组织，不把亿级 ID 塞入单个 JSON。可供 JavaScript 等客户端使用的长整数标识应明确编码，避免被意外转换为不精确数值。

DeliveryLayout 的分片记录至少含稳定存储引用、内容摘要、字节数、样本数、成员映射和生成运行。重新压缩可改变字节摘要而保持逻辑成员；验证逻辑等价需要检查成员、值与契约，不能只看文件数量。

布局必须固定所属发布与覆盖范围。宣称完整布局时，展开成员映射应与发布精确集合一致；子集布局须显式声明范围，Reader 核对计划所需范围被覆盖且符合授权，不能把缺失样本当作自动缩小计划。遗漏、重复、额外成员及错版分别检测；有意重采样属于计划。packing 等非一对一映射应可归因到源成员和输入规范，不能只比样本数。布局顺序本身不定义训练顺序；若计划依赖它，重排也要修订计划并核对检查点，不能热替换旧 layout_ref。

### 7.3 发布协议与失败恢复

推荐流程为：创建持久化 PublishIntent → 构建候选输出 → 验证引用、质量、用途与依赖 → 固定快照和制品 → 写入不可变清单 → 在发布登记事务中提交 published 状态与 Outbox → 下游按需构建服务投影。

候选构建和待提交依赖受准备期保留记录保护，避免发布与 GC 竞态。发布协调器崩溃后由对账恢复：查明清单、快照和登记状态，按 §6.3 判断能否继续或终止；不能仅凭超时删除可能已提交的结果。正式发布点是登记事务提交，不是某个文件出现。

PublishIntent 定位发布意图及关联的外部 operation，不能自行生成发布授权。提交发布状态、签发读取权限与实际分发前，核对执行身份、动作、目标、清单／布局摘要、数据用途、适用策略及有效授权；等待、重试或目标变化后重新核对，仍被既有有效授权覆盖时可以复用。候选处理、独立验证与发布权限分离；不能在持有发布凭据的上下文执行候选附带的脚本。

发布提交端还须核对期望目标修订和有效写权，将条件检查绑定到实际提交，防止检查后发生撤权、目标迁移或旧请求迟到覆盖新状态。跨系统无法原子核对的部分要声明一致性／撤销窗口及补偿责任，并通过故障测试证明满足所采用契约；协调端检查一次、持有凭据或请求取消均不等于已强制执行。

恢复流程沿用 §6.3 的未知操作规则；查询不完整时保持未知，不盲目完成或终止。回滚目标也须满足当前授权和策略。清单、签名与来源声明只提供各自范围的依据；同一逻辑发布的不同布局逐一绑定实际摘要及覆盖，不能用旧布局的证据直接放行新字节对象。

Iceberg 的原子提交与快照隔离不能直接扩大为整个平台的全局事务。[R03][R05] 多表一致性由构建计划、输入进度和发布校验建立。产品契约要求同时可用的接口须在发布前就绪；可选索引可独立暴露 building、ready、degraded 等状态。

### 7.4 内容不可变，可用状态可变

建议区分三个正交状态：构建状态（building／validating／qualified／failed）、发布状态（published／withdrawn）、访问可用性（available／restoring／degraded／unavailable）。策略还可以阻止特定主体或用途访问。

撤回不修改原清单；回滚通过显式变更可变别名或发布选择策略实现，并记录审计。长期训练必须固定 release_id，不能随 latest 别名漂移。发布状态、当前授权与保留状态不能被一个 ready 布尔值代替。

## 8. 面向学习与运行的专门契约

### 8.1 学习目标决定样本模型

| 场景 | 必须显式表达的内容 |
| --- | --- |
| 预训练 | 文档边界、来源、采样、分词、截断和拼接 |
| 监督微调 | 消息角色、输入／目标边界、模板、参与损失的 token |
| 偏好学习 | 共同条件、候选响应、偏好关系、评价准则和来源 |
| 强化学习／Agent 训练 | 任务、环境版本、观测、动作、轨迹、终止、奖励与验证器 |
| 评测 | 能力目标、输入条件、允许工具、评分规则、隔离与污染检查 |
| 多模态学习 | 模态版本、对齐关系、解码／预处理、缺失模态与同步容差 |

TRL 的 assistant-only／completion-only loss 和 packing 等配置影响监督或输入组织。[R17] 因此，相同文本不代表相同训练样本；相同样本集合也不代表相同学习分布。

建议把实际训练分布表达为多个发布及其采样过程的组合：P_t(e) = Σ_k α_k(t) P_k(e)。必须声明权重作用于样本、文档、token、时长还是其他单位，是否有放回、是否分阶段，以及如何处理耗尽和过采样。仅保存一组百分比不足以重建实际分布。

### 8.2 质量、去重、切分与泄漏

质量是任务相关的评价记录，不是资产上的永久单分数。结构有效性、用途准入、内容质量和模型收益分开评估。错误答案可能是有用的偏好负例；小说不应被当作需要事实核验的普通声明集合。

去重区分字节重复、近似重复和语义相似，并记录算法、阈值、簇和代表选择。切分归属属于具体发布或实验。按任务定义隔离单位：文档、会话、用户、设备、时间段或来源族；在构造样本前固定规则，并检查翻译、改写和合成后代是否造成泄漏。

这些隔离规则不是无条件适用于全部实验。例外须显式记录其评测目的与影响，不能在随机切分后再用“已去重”掩盖关联泄漏。下游模型收益需要独立评测，数据质量代理指标不能自动替代它。

### 8.3 Reader、分布式分配与检查点

ConsumptionPlan 应固定发布、布局、输入规范、混合策略、初始随机配置、分配算法及其版本；运行中演进的随机状态归入关联检查点，沿用 §7.1 的契约／进度分离。Reader 需要处理 worker／rank 变化、尾部分片、异常样本、重试和恢复，并区分有意重采样与无意重复。缺失或拒绝访问的必需输入应使消费受阻；如契约允许跳过／替代，须有固定规则、实际处置记录及对覆盖和采样的影响，不能静默修改计划或把不完整结果报告为完整。

PyTorch 文档指出，多进程 IterableDataset 的副本需要正确配置才能避免重复读取。[R18] 在本设计中，还要把“已下载、已解码、已预取、已交付、已参与已保存训练状态”区分开。恢复位置应与训练检查点协调，预取进度不能直接当作训练完成进度。

对于在线增强或动态混合，随机种子通常不够：还需记录算法版本、配置、分布式拓扑变化和可恢复状态。数值级复现还依赖模型、优化器和计算环境，超出仅固定数据版本的保证范围。

### 8.4 Context 与行动反馈

ContextManifest 记录任务、主体、策略决定、实际采用的 ContentRef、检索配置、工具结果与装配时间。需要严格回放时，保留实际结果制品；只保留查询文字不能重建变化中的检索结果。

不可信文档内容、受治理语义说明、可信运行策略和实际授权是不同层次。数据中的指令文本不能自动成为 Agent 的控制指令；语义元数据本身也需要来源、审核和信任边界。

动作链路至少区分 ActionProposal、AuthorizedAction、ExecutionReceipt 和 VerifiedOutcome。工具说“成功”不代表业务目标成立；反馈进入训练前仍需独立质量、权限和污染检查，不能把线上生成内容自动循环当作真值。

## 9. 管理、治理与生命周期

### 9.1 管理信息的权威边界

| 信息类别 | 权威来源 | 其他系统的角色 |
| --- | --- | --- |
| 资产身份与责任 | 资产登记 | 目录搜索与缓存为投影 |
| 表当前提交指针 | 表目录 | 平台登记只引用，不自行改写 |
| 发布内容 | 不可变清单与固定成员 | 发布登记绑定清单摘要 |
| 发布状态 | 发布登记 | 消息通知和目录索引最终同步 |
| 当前使用授权 | 策略执行与授权状态 | 历史批准仅作证据，不代替当前检查 |
| 投影覆盖与状态 | 构建记录和投影登记 | 可观测界面汇总显示 |
| 质量／来源结论 | 对应 Assessment／运行证据 | 总分与仪表盘为派生结果 |

Iceberg REST Catalog 提供表目录互操作，不能取代来源、用途、质量和产品发布管理。[R06] 资产目录可以统一呈现多种管理信息，但不能成为所有状态的第二套权威数据库。

### 9.2 契约、语义与兼容性

每个数据产品至少声明记录粒度、字段语义、单位、时间、空值、实体关系与基数、允许的聚合、质量门槛、责任方、用途条件和服务目标。ODCS 提供涵盖 Schema、质量、责任与服务等内容的契约结构，可作为交换与组织参考。[R19]

版本分别管理内容、Schema、语义、处理代码／配置、模型／模板、索引、发布、训练输入与策略。字段类型兼容不等于语义兼容；单位、枚举含义或连接基数变化可能不触发语法错误，却改变结果。

演化流程采用差异检查 → 影响分析 → 兼容性测试 → 双版本验证 → 迁移或新发布 → 明确退役。语义互操作项目如 Apache Ossie 值得跟踪，但其标准与实现采用应绑定发布版本和验证证据，不作为本平台内部模型的唯一依赖。[R20]

### 9.3 血缘与证据粒度

运行级血缘记录输入、代码、配置与输出；集合级血缘记录表快照、发布与制品关系；内容级证据定位某个标签、声明或样本所依赖的具体单元。OpenLineage 的 Job／Run／Dataset 模型可用于运行与数据集级互操作，精确内容证据由本平台补充。[R16]

批次清单和共享父节点减少重复元数据。只在审计、风险或任务需要的位置细化到记录和片段，不要求每个 token 复制完整来源链。血缘无法独立证明标注正确、证据充分或某条训练数据对模型结果的因果贡献。

### 9.4 保留、清理和撤回

普通 GC 以有效发布、准备中发布、运行检查点、读取租约及其他合法保留依据为根，沿依赖图计算保留集合。使用宽限期、二次检查和幂等删除处理并发变化，禁止只按“文件年龄”清理仍被引用的对象。

准备期 pin 或租约到期是触发对账的条件，不是可回收证明。未知操作、可能迟到的提交和仍有写权的旧 Worker 所涉及依赖，在完成效果核对、终止／隔离及引用重查前不能按普通孤儿删除。回收决定要与提交权协调，删除本身也按 §6.3 记录操作及未知结果；不能用“清理重试”绕开原发布的冲突范围。

Iceberg 的分支与标签也受保留策略影响，单独保存 snapshot_id 不等于永久保留文件。[R21] 必须同时协调表维护任务、对象生命周期规则和平台依赖登记。权限撤回或合法删除要求可能优先于普通复现性保留，应显式作出决定并标记受影响发布不可用。

撤回流程分别处理新授权、正在运行的任务、索引与缓存、物理副本、第三方交付和影响记录。已经下发的凭证有其到期与撤销能力边界；被下载的数据不能仅靠修改平台状态收回。删除检索索引不会自动改变已训练模型参数，模型影响需要独立登记和处理。

撤回从具体来源版本、ContentRef 或用途范围出发，按依赖与适用策略识别受影响的样本、发布、布局、混合计划和运行；重新打包或生成新 ID 不会自动解除限制。不能证明某部分不受影响时，不继续以旧批准放行该部分；可按契约扩大隔离范围并核对。已撤回依赖不通过原地删成员来“修好”旧发布，需要新的过滤结果或新发布以及相应计划修订。保留依据和历史发布时间不构成当前使用授权。

保留的审计、哈希和日志也可能含敏感信息，不能以“只是元数据”为由绕过用途和保留规则。加密、密钥轮换和不可变保留必须与删除流程共同设计，避免形成技术上无法履行的冲突承诺。

## 10. 运维、性能与故障模型

### 10.1 以三类指标观察系统

| 维度 | 最低观测项 |
| --- | --- |
| 正确性与治理 | 引用完整性、重复／遗漏、连续提交缺口、发布检查、越权拒绝、撤回积压 |
| 时效与可用性 | 接入积压、处理／发布延迟、索引覆盖、新鲜度、恢复状态、读取失败 |
| 效率与成本 | 输入／输出字节、请求数、解码耗时、缓存命中、文件尺寸、单位样本或 token 成本 |

指标应说明分母、采样窗口和例外，避免只报成功率而隐藏永久隔离数据。故障重试、超时、取消和主动拒绝需要可区分；可预期的策略拒绝不应误归类为系统故障。

用资源需求估算初始预算，例如在途内存约为吞吐乘以在途时间，再加解码与输出放大；真正门槛由负载实测决定。训练看有效输入速率与数据等待占比，检索看授权后的质量和延迟，发布看完成时效与依赖完整性，不能使用单一 QPS 比较全部路径。

### 10.2 提交域、隔离与灾难恢复

每组权威状态有明确提交协调域。跨区域复制需要定义延迟、切换流程和写入 fencing，避免故障期间两个区域同时合法修改同一提交指针。控制面、数据面和后台重建应按资源与故障边界隔离。

灾难恢复需要同时覆盖控制数据库、目录元数据、对象、密钥、配置和发布清单。恢复必须验证引用闭包与实际可读性；“备份任务成功”不是恢复演练。RPO（允许丢失的数据窗口）与 RTO（恢复时间目标）按数据产品确定，当前未给定数值。

### 10.3 故障场景与预期行为

| 故障 | 预期行为 |
| --- | --- |
| 对象已写入，登记失败 | 重试识别已存在内容；对账恢复或受控回收孤儿 |
| Worker 写到一半退出 | 部分输出不可正式发布；新尝试不混用残留 |
| 旧 Worker 在租约失效后提交 | 旧写能力未停止或可靠隔离前不授予新写权；实际目标端拒绝迟到写入 |
| 表已提交，发布登记请求结果未知 | 候选数据受保护；核对 intent、实际登记及迟到效果，未知时限制冲突写入，不盲目重试 |
| Outbox 或消费端重复投递 | 复用事件身份；同一逻辑结果不重复提交 |
| 索引局部构建失败 | 暴露缺口／降级，不能以最近更新时间伪装完整 |
| 清理与读取／发布并发 | 租约、准备期 pin 和二次校验阻止误删 |
| 权限在计划生成后变化 | 按声明时效重新校验／拒绝，审计记录真实暴露窗口 |
| 新模板复用旧 token 布局，或重排布局沿用旧读取游标 | 核对输入规范、成员映射与检查点；不兼容则受阻或显式迁移，不能静默换绑 |
| 发布时证据通过，之后生产者撤销或出现可信失败 | 保留历史清单，读取新增证据与撤销记录，按当前上下文重新判断 |
| 撤权后才发现发布早已提交 | 记录已发生效果与合规判断，阻止未获准的新动作，受控处置而非改记失败并重试 |
| 准备期 pin 到期但发布请求可能迟到 | 保持未知依赖保护，核对／隔离提交后再决定回收，不能凭到期删除 |
| 区域故障或控制库恢复 | 单一写权恢复后校验依赖与清单，再恢复正式消费 |
| 异常大样本／解压膨胀 | 资源预算阻断或隔离，不拖垮全部 Worker |

## 11. 参考实现与选择依据

### 11.1 可替换技术骨架

| 能力 | 参考实现 | 采用条件与边界 |
| --- | --- | --- |
| 持久化载荷 | 对象存储 | 验证条件写、校验、权限、复制、保留和恢复 |
| 批量结构化数据 | Iceberg＋Parquet | 引擎共同验证类型、快照、演化与维护功能 [R02][R03][R04] |
| 控制状态 | PostgreSQL 等事务数据库 | 满足唯一约束、Outbox、备份和并发提交需求 |
| 批量精确查询 | Trino 等查询引擎 | 验证类型映射、权限、快照读取和查询隔离 [R13] |
| 增量与解耦 | Kafka；按需 CDC／Outbox | 不把外部系统自动纳入事务保证 [R14][R15] |
| 计算交换 | Arrow／Flight | 明确内存所有权、端点授权与预算 [R10][R11] |
| 训练交付 | 版本化 Reader；按负载选择分片格式 | WebDataset 是 tar 分片的一种实现，不是治理系统 [R22] |
| 血缘互操作 | OpenLineage | 运行血缘之外补充内容证据与发布依赖 [R16] |
| 语义与发现 | 资产目录＋受治理语义定义 | 按需映射开放标准，不要求全球统一本体 |
| 服务投影 | 全文、向量、图或低延迟索引 | 由真实查询需求和质量评测触发 |

选择一个主开放表格式作为初始基线，减少重复目录、双写和运维表面；已有系统能够满足契约时优先复用。不同存储形态有明确负载收益后再引入，不因为架构图出现某个词就部署对应数据库。

### 11.2 规范成熟度与能力矩阵

截至本次核查，Iceberg 官方规范将格式 v1～v3 标为已采用，v4 仍处于开发中。[R03] 生产选择应是“格式特性 × 写入引擎 × 查询引擎 × 维护工具”的共同支持交集，而非最高版本号。

对候选组合，至少验证：目标类型和空值往返；时区与精度；字段／分区演化；并发写；删除与压缩；快照保留；错误恢复；权限粒度；发布清单解析。规范支持、某个库支持和现网已验证是三个不同状态。

新技术跟踪只记录会改变契约或显著改善负载的变化。Apache Ossie、ODCS、Arrow 或表格式更新都可以被评估，但不以“AI-native”标签代替兼容性与收益证据。

## 12. 从当前建设阶段落地

### 12.1 先做一个真实数据产品

第一期固定一个来源、一个主要模态和一个明确消费任务。建议先交付一份能被真实 Reader 读取、可追溯且可重建的数据集，再决定是否立即启动训练。来源可以是文档、事件或媒体，不能因为示例使用文档就把平台设计成仅支持文本。

首先冻结三份契约：来源契约、身份与版本契约、数据集发布契约。来源契约包含粒度、身份、增量位置、格式、单位、时间、更新、删除、用途、失败和回补语义。未知用途进入隔离或待批准状态，不默认允许训练。

### 12.2 四个建设里程碑

| 里程碑 | 建设范围 | 完成门槛 |
| --- | --- | --- |
| M0 来源与版本闭环 | 契约、原始接纳、登记、校验与回读 | 重复不产生重复逻辑版本；来源更新产生新版本；旧版可读 |
| M1 处理与证据闭环 | 一个真实解析／清洗流程、运行与质量记录 | 输出追到输入和处理版本；失败可重试；隔离数据可再处理 |
| M2 正式发布闭环 | 配方、成员、切分、清单、依赖与保留 | 新输入不改变旧发布；缺引用或用途不符不能发布 |
| M3 消费与故障验收 | Reader、实际批次、授权、故障注入、恢复与观测 | 正常消费可验证；越权被拒；中断不暴露半成品；恢复语义明确 |

权限、备份和审计从 M0 就实施，M3 是综合验证而非补做安全。每个里程碑保留通过的证据与未执行项；不以“已经部署几个服务”衡量完成。

### 12.3 一期交付包与仓库结构

建议交付契约、Schema、接入器、一个处理器、发布器、Reader、验收测试和运维手册。它们可以是一个模块化应用和若干作业，不需要预先拆成大量服务。

```text
contracts/       来源、产品、用途与兼容性契约
schemas/         引用、内容、样本和清单 Schema
recipes/         版本化构建、切分与采样规则
pipelines/       接入与处理作业
publisher/       intent、校验、发布、对账
readers/         发布解析、分片读取、恢复接口
tests/           不变量、兼容性、故障与负载测试
ops/             备份、恢复、清理、撤回与值班手册
docs/decisions/  ADR 与证据索引
```

运行数据、密钥和临时凭证不进入代码仓库。CI 校验契约引用、Schema 变化、样例解析和不变量测试；环境级测试记录引擎、配置、输入数据和代码版本。

### 12.4 由需求触发的扩展

知识图谱在实体对齐或关系推理有明确价值时引入；向量检索在存在在线检索任务与质量基准时引入；LLM 标注在标注规范和独立验证就绪后引入；多模态专用存储在随机访问或解码瓶颈被测量后引入；Agent 接口在受控访问与动作契约成熟后引入。

“预留”意味着公共引用与契约不堵死后路，不意味着提前建立几十张空表。当前没有实时性要求的链路可以批处理，已经可靠的执行系统不必为了统一而重写。

## 13. 验收矩阵与实施前待决事项

### 13.1 可执行的完成标准

以下是共享验收规格，当前均为 **NOT RUN**。消费项目应按固定指南版本记录适用条目、例外及责任；实际结果、代码／配置／数据版本和证据位置留在该项目的任务或运行记录中。不得只修改本文状态来宣称通过，也不把某个消费项目的 PASS 传播成所有项目的完成事实。原文 G01–G12 在本仓库使用 DM-G01–DM-G12，验证目标仍属于数据平台范围。

| Gate | 验证目标 | 最小证据 |
| --- | --- | --- |
| DM-G01 身份与版本 | 重复接入幂等；来源更新保留旧版 | 自动化输入／登记／回读断言 |
| DM-G02 引用解释 | 指定 ContentRef 可定位；Schema 与坐标明确 | 正反例、边界区间和未知版本测试 |
| DM-G03 发布原子可见 | 中断不暴露半成品；未知结果先核对；候选不能自定证据或替换已批准对象 | 各提交点、响应丢失、查询不完整、迟到／撤权的故障注入；自报 PASS、缺证、新失败／撤销、换清单摘要的拒绝记录 |
| DM-G04 精确成员 | 重建或重新读取得到声明范围的精确成员与版本；子集不冒充完整发布 | 遗漏／重复／额外／错版、非一对一映射及计划覆盖比对 |
| DM-G05 学习语义 | 发布内容与消费配置分别修订；模板、掩码、截断、packing、采样符合声明 | 小样本监督断言；修改答案与仅换模板的版本归属；新规范复用旧预计算布局的拒绝测试 |
| DM-G06 切分与污染 | 指定隔离单位不无意跨集合 | 重复／同源／派生后代对抗样例 |
| DM-G07 授权与撤回 | 发布及 SQL、对象、检索、缓存和导出不能越权；恢复不沿用已失效批准 | 权限矩阵、等待后撤权／换对象、旧计划／缓存命中、长流／预取、来源撤回传播及回滚的窗口验证 |
| DM-G08 保留与清理 | GC 不破坏有效或未知在途依赖；确认终止候选可受控回收 | 并发读取／发布／清理、pin 到期后迟到提交与删除结果未知的测试 |
| DM-G09 恢复与 fencing | 旧写权未确认失效不产生第二写入者；恢复后引用完整 | 失联、租约过期、共享工作区／对象／提交端迟到写入及完整恢复演练 |
| DM-G10 资源与性能 | 指定负载满足容量、延迟与成本约束 | 固定环境基准、尾延迟、内存与成本报告 |
| DM-G11 兼容性 | 目标引擎组合的类型与维护行为一致 | 版本固定的互操作测试矩阵 |
| DM-G12 消费端到端 | Reader 构造真实批次并按固定计划恢复；迁移显式记录，不静默跳过必需输入 | 消费冒烟、布局重排／计划修订、随机状态与检查点兼容性、必需输入缺失／拒绝及重复／遗漏测试 |

数据接口和监督断言通过仍不代表模型能力提升。正式数据效果结论需要独立评测集、实验配置、结果与不确定性说明。

### 13.2 尚需以真实环境确定的事项

| 待决项 | 必须取得的输入 | 形成的决定 |
| --- | --- | --- |
| 首个数据产品 | 来源、主要模态、消费任务、负责人 | 一期范围与产品契约 |
| 容量与 SLO | 日增量、对象分布、读取模式、峰值与恢复要求 | 预算、分片、缓存、RPO／RTO |
| 权限与保留 | 租户、区域、用途、授权时效和撤回要求 | 存储安全域、访问与生命周期规则 |
| 引擎组合 | 已有组件、运维能力、目标特性 | 兼容性矩阵和锁定版本 |
| 复现等级 | 需要成员一致、输入一致还是数值复现 | 清单、索引／制品与执行状态保留范围 |

这些问题不阻碍先设计公共引用和发布契约，但会决定物理资源与具体部署。理想环境表示目标能力完整，不表示可以忽略成本、资源上限和失败。

## 14. 贯穿示例与决策摘要

### 14.1 一份维护手册的完整生命周期

接入手册 manual_123@r3，登记来源、摘要、结构契约与用途条件。解析运行产生新的文本、结构节点、表格和页面映射资产；ContentUnit 引用解析版本，必要时通过映射回到原始页面。

查询端可筛选某设备系列的有效材料；检索索引返回明确 ContentRef 与索引版本。问答构建运行将问题、证据、目标回答和评估组成样本，固定切分后形成 rel_007。其逻辑成员不因后续压缩、重分片或索引重建改变。

训练作业固定 rel_007、layout_003、输入规范和采样计划；实际读取状态与训练检查点协调。Agent 另行记录它真正选用的证据与工具结果，不把“可检索的所有材料”冒充“本次实际上下文”。

手册更新为 r4 时，原始版本、解析结果和派生索引分别产生新状态。在线检索按新鲜度契约更新，冻结发布仍指向旧版；如果旧内容被撤回，发布状态与当前授权阻止新的不允许使用，并登记既有训练运行的影响范围。

### 14.2 向结构化事件场景迁移

在设备信号场景中，原始采集文件或批次是资产版本，观测记录按设备、信号、时间与质量状态解释。解析结果必须引用协议／映射版本、单位与时间基准，不能只引用一段匿名 f32 数组。无效、未采样、未知和零值要区分。

逻辑上可以定义观测关系，物理上采用宽列、按信号组组织或专用列式布局；不要求用逐信号长表承载所有热路径。训练样本可能是带重采样、对齐、掩码和标签的时间窗口，必须记录这些派生规则。Kafka 分区、Parquet 文件和训练窗口分别服务传输、存储与学习，不能互相充当身份。

这一迁移说明：统一底座应覆盖文档与事件，但不强迫两者共享同一个载荷 Schema。业务协议和采样语义保留在领域模型中，平台统一版本、引用、发布、权限和证据。

### 14.3 建议登记的架构决定

| 决定 | 理由与代价 |
| --- | --- |
| 身份、版本、位置分离 | 允许迁移与多布局；增加引用解析与登记责任 |
| 领域、学习、运行模型共享底座 | 避免万能对象；需要治理跨模型关系 |
| 发布、布局、消费计划分离 | 同时服务查询与训练；需要更多明确版本 |
| 单一提交权威＋跨系统对账 | 边界可验证；接受暂态与恢复流程 |
| 默认至少一次＋幂等效果 | 适合异构系统；要求可证明的去重与提交协议 |
| 全对象直读须全对象授权 | 阻止绕过细粒度权限；部分场景需物化结果 |
| 保留与撤回沿依赖执行 | 降低误删和隐性副本风险；增加生命周期复杂度 |
| 真实数据产品驱动建设 | 优先获得端到端证据；部分目标能力分阶段实现 |

以上均为本版 Proposed 决定。批准时应按项目 ADR 流程记录适用范围、替代方案、已知代价和验证证据，不把本文编号直接冒用为既有仓库的 ADR 编号。
