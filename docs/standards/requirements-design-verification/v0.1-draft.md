# 需求、设计与验证衔接方法

版本：`v0.1-draft` r1；状态：**Proposed**；日期：2026-10-26。维护责任：Daedalus 项目维护者，消费项目对自身需求、设计决定、检查入口与接受负责。

本方法帮助项目负责人、工程师与 Agent 把问题转成可验收能力，再把设计承诺映射到有效检查。它是供首个真实任务校准的短方法候选，不是已经验证的流程或完整教材。小修复可用一段任务说明加验证记录完成，不强制新建 PRD、ADR、模板目录或所有检查类型。

## 2. 从问题到能力契约

先核对使用者、当前障碍和依据，再形成方案。事实、假设和偏好分别标注；不能把“采用某项技术”直接当成产品价值。

| 推导步骤 | 应回答的问题 | 留下的最小结果 |
| --- | --- | --- |
| 问题与场景 | 谁在什么输入、环境或故障下受影响？当前结果是什么？ | 可定位的反馈、复现或观测；未证实的需求标为假设 |
| 使用者结果 | 完成后能做什么？不做会怎样？ | 能实际演示的能力目标与接受责任 |
| 范围与依赖 | 包含、排除什么？哪些约束不能改变？ | 非目标、外部依赖、现有契约与受影响对象 |
| 四维质量 | 产品价值、设计、实现、交付维护分别要求什么？ | 正常、边界和失败行为；性能、资源、兼容性与使用条件 |
| 未知与探索 | 哪个假设可能推翻方案？验证要投入多少？ | 有限实验、结果判据、责任与停止条件；关键未知阻塞对应承诺 |
| 接受与修订 | 什么证据说明完成或未完成？目标变化由谁决定？ | 版本化接受条件、观察窗口与显式变更依据 |

“提高解析器稳定性”需进一步限定错误输入类型、允许的部分结果、可诊断错误、正常行为和资源上界。约束来自产品与环境，不由执行器随意补一个容易通过的阈值。无法确定的关键判据保留待决，先完成不依赖它的调查。

完成判据：另一位工程师或 Agent 能复述目标、预测边界行为，并指出至少一种意味着没有完成的结果。方法完成只表示足以进入对应设计或评审，不意味着 Capability 已被接受。

沿用既有 Capability / Task 的 ID 和 revision。需求变化后记录继续旧版本、取消或显式迁移；不把正在运行的 Task 静默改绑到新 revision。探索可以得到“不值得继续”的有效结果；执行节奏和授权复用见 [Agent 工作流](../../agent-workflow.md)。

## 3. 从约束到设计与决定

按“约束与质量 → 边界和状态 → 关键性质 → 接口与机制 → 替代方案 → 验证依据”推导。以下问题可写在现有设计或任务记录中，篇幅随失败后果、未知程度与可逆性调整。

1. **边界与责任。** 标出使用者、输入输出、外部依赖、信任边界，以及哪些责任本组件不承担。先检查已有工具能完整承担哪些义务，再确定自研差异。
2. **身份、状态与所有权。** 区分稳定 ID、内容 revision、状态投影；说明哪个来源具有权威，谁能写入，资源怎样取得和释放。不同组件不能各自宣称拥有同一事实。
3. **性质与失败。** 区分“不发生错误行为”的不变量、“在前提下最终进展”的要求和统计性能目标。列出超时、部分完成、重复、取消、依赖不可用及恢复后的行为；不能用重试掩盖结果未知。
4. **机制与接口。** 为关键性质标出实现机制、外部假设、错误语义、资源边界、版本演进与诊断入口。检查组合是否满足下游前提，而不只画正常路径。
5. **替代与取舍。** 比较至少一个合理替代，包括保持现状或复用现成组件；说明质量、复杂性、成本、维护及退出路径。没有证据的优势记为待验证假设。
6. **决定与复审。** 记录选择、依据、接受责任、限制，以及什么变化会使决定失效；长期重要取舍遵循项目自身 ADR 约定，Daedalus 的规则见 [ADR 入口](../../adr/README.md)。

完成判据：设计解释为什么这样划分、哪些条件会使方案失效，以及关键承诺如何验证。选型、原型成功和设计审阅都不自动放行生产。发布／部署职责继续按 [供应链指南候选](../software-supply-chain-security/2026-edition-draft.md) 的独立采用范围评估，不把该 Proposed 指南隐式变成全项目要求。

## 4. 从接受条件到检查集合

对每项关键要求，先描述违反方式，再设计能区分正确和错误行为的测试判据（oracle）。判据可来自业务契约、固定预期结果、独立参考实现或可论证的性质；不能从被测实现原样复制同一假设。选择便宜且足以回答问题的层次，需要组合行为时使用真实接口与环境。

| 要求示意 | 需要验证的行为 | 方式与对象 | 判据与剩余边界 |
| --- | --- | --- | --- |
| 正常输入不退化 | 输出与既有语义一致 | 固定语料、候选版本的回归与集成检查 | 预期输出或独立差分；不代表任意输入正确 |
| 错误输入可诊断 | 非法长度、截断或未知类型产生约定错误 | 真实解析入口的边界与负例；适合时增加性质／模糊测试 | 错误分类、退出与部分结果；无崩溃不能单独证明正确 |
| 中断后可恢复 | 已完成与未完成部分按契约处理 | 授权隔离环境中的有界中断、回放与恢复 | 恢复后实际结果及在途操作；进程死亡不证明外部效果未发生 |
| 资源与性能满足目标 | 指定工作负载下保持约定行为及资源界限 | 固定候选、环境、代表性负载与基线 | 正确性同时成立，再比较时间与资源；不跨平台直接推断收益 |
| 可交付与可维护 | 用户能取得、使用、诊断和升级／恢复 | 实际制品与目标使用路径 | 安装或调用结果、兼容性和恢复记录；构建成功不等于可用 |

此表是方法示意，未运行。具体要求、数值、命令、测试数据与判据由消费项目维护。并发协议可按风险选择性质检查、模型或线性化测试；故障注入、负载和权限负例必须先明确目标、隔离、授权、预算与停止条件，不从方法示例推定可操作生产。

每份验证计划把“要求／违反方式 → 检查 → 输入与环境 → 受测版本／制品 → 判据 → 证据位置 → 未覆盖项与责任”连接起来。正常、边界、错误、恢复和兼容组合按风险选择；不适用须有依据，未实现、缺环境或暂时无法运行不能填为不适用。

检查集合形成后再映射到 [Git/GitHub v1.1](../git-github-workflow/v1.1.md) §25、§31 的 Fast / Plan / Affected / Full / Extended。**本节的验证设计不是 CI Plan 的执行输出**：Plan 依据版本化规则选择覆盖但不执行测试，缺失或非法计划不能被这张表替代。PR-full 不要求未使用的 Affected 入口；Full 覆盖当前集成契约，Extended 中属于发布必需的检查仍须在发布前满足。

可信生产者、证据完整性、语义覆盖、实际结果和 applicability 分别判断。适用的可信失败证据仍然是失败；缺失、超时、工具错误、未知和未运行不改写为通过。候选、输入、规则或环境改变后，重评证据适用性，保留失败及相矛盾记录。本地证据不冒充 Required Check，多个 PR 分别通过不代替组合验证，设计批准不替代发布授权。

完成判据：检查能发现它声称防止的错误，判据及覆盖缺口可解释。可通过已知缺陷、受控变异或错误样本验证检查本身的辨别力；没有必要为低影响文字修改堆砌测试数量。测试全绿只支持已验证范围，能力接受仍由契约指定责任人判断。

## 5. 在一个真实任务中校准

首轮在[消费接入与 G2 准备方案](../../plans/consumer-adoption-g2.md)的候选确认后，选择同一能力贯穿三个环节；目前没有消费者接受本方法，也没有端到端运行证据。

| 校准点 | 要留下的结果 | 不能替代它的材料 |
| --- | --- | --- |
| 问题到能力 | 真实需求依据、固定接受条件、未决项处置 | 一份字段齐全但没有使用者的空模板 |
| 能力到设计 | 关键性质、替代方案、复用／自研决定及反例 | 仅有架构图或预先选定技术栈 |
| 设计到验证 | 要求映射、具有辨别力的检查、真实环境及失败边界 | 测试数量、代码覆盖率或模型总结 |
| 验证到使用 | 同一交付对象、能力接受、反馈与后续判断 | PR 已合并或示例中的成功声明 |

记录准备和维护成本、遗漏与返工、总尝试成本和实际使用效果；没有可比基线时仅报告观察。第一例完成后再决定拆分指南、发布固定版本或封装 Skill。维护、勘误、来源失效与升级规则见[共享内容目录](../README.md#维护勘误与版本演进)。
