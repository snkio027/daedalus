## 1. 定位与现有规范的关系

本指南解决的是：交付的对象来自哪里，如何构建，哪些证据支持使用它，以及谁能在什么条件下发布和部署。供应链控制服务产品与交付质量，不替代功能正确性、用户价值或运行可靠性判断。

| 依据 | 权威范围 | 本指南的补充 |
| --- | --- | --- |
| [产品契约](../../product.md) | 四维质量、三循环与完整能力增量 | 将供应链风险纳入相应交付与维护要求，不把全部项目容器化 |
| [Architecture v0](../../architecture.md) §1.4、§5、§7–8 | 不可变制品、授权、外部操作、证据适用性与能力验收 | 为制品来源、构建和部署证据提供具体检查对象 |
| [Git/GitHub Workflow v1.1](../git-github-workflow/v1.1.md) §25–35、§44–45 | 仓库验证、集成与发布规则 | 在消费项目选定的验证入口和发布流程内落实控制，不另建竞争门禁 |
| [Daedalus 工程约定](../../engineering.md) | 固定来源、Profile / Instance、采用决定与实际配置 | 明确哪些要求适用、谁实施及怎样取得运行证据 |

v1.1 的 `PR-full / Queue` 与 `standard / assured` 继续分别决定集成路径和保证等级。本指南不改变 Plan / Full 契约，也不将采用签名或 SBOM 等同于升级为 assured。影响仓库准入、验证策略或发布权限的变更，继续走所采用规范的审查与授权流程。

standard 的策略审查和适用失败处置依赖可信维护者 / 独立审查者及原生保护，不能报告为机器独立核验；assured 另须实现并验收 v1.1 §26.3 的核验与检查发布边界，未接入时保持阻塞。该区分适用于两种集成路径。发布检查、签名或部署准入不能补偿缺失的 PR 必需 Plan / Full，也不能把 Queue 的入队绿灯变成合流通过；发布系统还须核对实际集成与获准发布来源的关联。

## 2. 交付链与对象身份

```text
源码与依赖 → 构建 → 不可变制品 → 验证与发布判断 → 分发 / 部署 → 运行反馈
    │          │         │              │                 │
    └──────────┴─────────┴── 来源、日志与证据关联 ───────────┘
```

这是一组关联关系，不规定必须创建几个 Workflow。验证可以发生在多个阶段；部署也不是库、CLI 或文档项目的统一必经步骤。

| 对象 | 应固定的身份与上下文 | 不能替代它的东西 |
| --- | --- | --- |
| Source | 仓库、完整提交、构建上下文、锁文件及实际解析的依赖 | 分支名、PR 编号、未经解析的版本范围 |
| Build | 运行及 attempt、构建器、构建定义 revision、参数、平台和已记录输入 | “CI 成功”或一个可变 Workflow 文件路径 |
| Artifact | 仓库位置、内容 digest、类型；多平台时记录 index 与实际平台对象的关系 | tag、Release 标题、下载文件名 |
| Evidence | subject、生产者、内容完整性、方法、结果、覆盖、时间及规则版本 | 文件存在、链接可打开或一项通用绿色状态 |
| Deployment | 目标环境、操作身份、期望与实际制品、配置 revision、观察时间 | 部署请求已发送或分支当前 HEAD |

同一已验证制品向环境提升；重新构建产生的对象重新核对身份及所需证据，不能仅凭相同源码提交继承旧结果。PR head、test-merge、merge-group 与最终集成提交分别记录；从其中一个对象构建的制品不自动成为另一个对象的发布候选，复用须有已接受规则与可复核的等价依据。制品与配置共同影响运行行为，配置变化也要评估原证据的适用性。

## 3. GitHub Actions 的组织与信任边界

Workflow 由事件或调用触发，Job 承担执行与权限边界，Step 在 Job 中按流程运行。不要把 Job 名称或“security”标签当作隔离机制；实际 Runner、身份、工作区、凭据、缓存及数据传递决定隔离是否成立。

同一 Workflow 的 Job 可以通过 `needs` 表达依赖；调用 reusable workflow 的 Job 也可以参与这种依赖。Reusable workflow 通过 `workflow_call` 暴露接口，在 Job 层调用；跨仓库调用需要 `@ref`，消费配置按已采用规则固定完整提交。`needs` 不能直接引用另一个独立 Workflow 的 Job。[Workflow 语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idneeds)、[复用工作流](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)

可以采用一个 Workflow 中职责分离的 Jobs，也可以按权限、触发时机、生命周期、复用或维护责任拆分 Workflow。文件长度不决定安全性；`01-ci`、`02-build` 等文件名不建立执行顺序。拆分后必须显式传递并校验源运行、候选与制品身份，不能靠“最近一次成功”关联结果。

`workflow_run` 的 completed 事件本身不代表上游成功，而且下游可能获得上游没有的 secrets 和写权限。需要核对上游 conclusion、来源仓库及事件、run / attempt、提交、目标与制品 digest；不能在特权下游执行来自不受信任 PR 的脚本或未经校验的产物。仅检查上游名称或成功状态不足以建立信任。[GitHub 的事件及安全边界](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run)

摘要校验成功只说明收到预期字节，不使其中的脚本可信。特权核验 / 签名 / 发布步骤将候选报告作为数据处理，不执行附带的安装钩子、验证脚本或恢复缓存中的程序；解析器、解包路径及参数处理也属于受保护实现。候选执行与发布不能共享可被前者污染的持久工作区、进程或 Runner 权限；分成两个 Job 不能单独保证隔离。[GitHub 工作流安全参考](https://docs.github.com/en/actions/reference/security/secure-use)

消费项目继续拥有 Fast、Plan、Full 等入口以及风险相关检查；CI 成功仅说明相应对象在声明覆盖内满足检查。构建时产生来源信息，后续扫描可以增加证据，但不能凭后置安全 Job 的自述重建一份可信构建历史。确需动态运行镜像时，验证环境仍不得持有生产权限。

## 4. OCI、构建与存储

### OCI 对象与 digest

OCI image manifest 关联配置和文件系统 layers；image index 可以关联多个平台的 manifest。OCI 也可表达关联制品；具体 Registry 是否支持存放、发现、复制和保留相应签名、SBOM 与证明，需要实测。`subject` 关联和同仓库存放都不自动建立信任。[OCI manifest v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/manifest.md)、[OCI image index v1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/image-index.md)

tag 可以移动，digest 用于识别内容。验证、授权与实际分发 / 拉取须绑定同一不可变对象；仅在记录中写 digest、执行时再从 tag 解析对象仍存在替换窗口。容器部署应使用核验过的 digest，或由受保护流程解析并固定 digest，最终准入再核对实际对象；多平台时须核对平台对象属于获准 index。不能将 amd64 的扫描结果直接当作 arm64 的结果，也不能把签过 index 当作全部平台均已扫描。

### BuildKit 与多阶段构建

BuildKit 可在构建时生成 provenance 和 SBOM attestation；是否生成、包含什么信息，以及导出后是否保留，受配置、driver、exporter 和存储方式影响。不能仅因使用 BuildKit 就声明已获得可验证证明；应在最终分发位置读取并核验。[Docker 构建证明](https://docs.docker.com/build/metadata/attestations/)

多阶段构建允许选择性复制运行所需内容，从而减少不必要的编译工具和中间文件。运行镜像中的依赖取决于程序实际需要，不能一概认定存在源码、Python 包管理器或某个工具就是错误。基础镜像、依赖、目标平台和构建输入应可追溯；固定依赖仍需配套更新与漏洞处理。[Docker 多阶段构建](https://docs.docker.com/build/building/multi-stage/)

构建需要私有依赖时，采用工具提供的 secret / SSH 临时挂载等机制，并检查日志与输出中是否泄漏。[Docker 构建秘密](https://docs.docker.com/build/building/secrets/)。本指南要求同时评估构建脚本的可信性：临时挂载只解决凭据注入方式，不保证读取凭据的代码可信；不要向不受信任候选暴露发布凭据。该原则与架构中的执行、验证、发布身份分离一致。

### 缓存与交付物

缓存是可丢弃的加速数据，不是唯一证据存储；命中缓存也不是检查通过。制品和证据需要可定位、可校验且符合保留及访问要求的存储。消费项目应核对缓存的写入者、作用域和失效规则，避免低信任执行污染高信任构建。

保存策略覆盖待发布对象、运行中的版本及恢复所需版本，也覆盖判断所需证据。清理 Registry、复制镜像或过期 Actions artifacts 后，要确认签名和证明仍可取得；不能留下可部署镜像却删除验证它所必需的对象。

## 5. SBOM、扫描、VEX 与 provenance

| 证据 | 主要回答 | 不能单独证明 |
| --- | --- | --- |
| SBOM | 工具在声明范围内识别了哪些组件及关系 | 组件完整无遗漏、没有漏洞或能够安全运行 |
| 漏洞扫描 | 指定工具和数据库在特定对象上发现什么 | 未发现就没有漏洞；所有发现都可利用或都应阻断 |
| VEX | 特定发布者对产品与漏洞影响作了什么判断 | 漏洞已经修复、所有版本均不受影响或可永久豁免 |
| Provenance | 构建器声明对象如何产生、使用哪些输入与参数 | 构建过程绝无入侵、所有输入完整或产品正确 |

SBOM 是数据，SPDX / CycloneDX 是常用表示，Trivy 等工具可以生成或扫描 SBOM。应记录工具版本、生成对象和覆盖；例如只扫描应用依赖不能声称覆盖整个容器及系统包。格式支持和扫描能力须按实际工具核对。[Trivy SBOM 文档](https://trivy.dev/docs/latest/supply-chain/sbom/)

扫描结果应绑定精确制品、扫描器及数据库版本或快照、扫描时间、配置、覆盖和实际退出结果。策略明确阻断条件、时效及失败处理；扫描器错误、缺失数据库、超时或输出缺失不是“零漏洞”。新漏洞和数据库更新可触发对同一制品的重新评估，不抹去历史扫描事实。

VEX 的 `not_affected` 等状态是有范围的声明。采用时核对发布者、产品 / 版本、漏洞身份、状态、理由、时间和更新关系；消费者决定是否信任以及何时复核。不能用无责任人、无适用对象的忽略项代替判断，也不能将 VEX 文件存在视为清除全部发现。[OpenVEX 规范](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md)

Provenance 必须对照期望验证 subject、生产者、构建定义和相关输入，而非只检查 JSON 字段存在。SLSA 按规范版本、track 与 level 定义要求；生成 provenance 或使用 Cosign 不自动满足某个等级。本指南不承诺等级，消费项目需逐项评估相应构建与来源控制。[SLSA v1.2 tracks](https://slsa.dev/spec/v1.2/tracks)、[制品验证](https://slsa.dev/spec/v1.2/verifying-artifacts)

## 6. 身份、签名与证据判断

OIDC 可让 Workflow 按信任关系换取短期凭据，减少持久密钥的分发。接入时限制 issuer、audience、subject 及适用 claims，并核对仓库、ref / environment、工作流身份与权限。取得 OIDC 身份令牌不等于云端已接受交换或拥有目标操作权限；即使取得访问凭据，也不代替业务发布授权。[GitHub OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect)

Cosign 等工具可验证签名和证明；keyless 验证仍须限定可信证书身份与 OIDC issuer，使用密钥时则需明确可信密钥及轮换 / 撤销规则。验证要针对预期 digest 和声明类型，不能只接受“任意有效签名”。有效签名提供完整性及来源关联，不能保证签名者未受入侵或内容安全。[Cosign 验证](https://docs.sigstore.dev/cosign/verifying/verify/)

Attestation 是带有 subject 和声明内容的证明对象；签名建立可验证关联，不自动确认声明为真。GitHub artifact attestations 同样需要实际验证，官方明确说明它们不保证制品安全。验证器与发布策略应有受保护的来源，不能让候选补丁自行降低对自己的要求。[GitHub 制品证明](https://docs.github.com/en/actions/concepts/security/artifact-attestations)

核验先取得已接受策略中的必需命题、覆盖和信任根，再检查实际证据，不能把候选上传的清单当作全部要求。签名身份、构建身份与验证身份分别核对；受信任签名 Job 不能仅替任意上传的 JSON 签名，就把其自填的 builder、源码或“测试通过”提升为可信事实。生产链须将声明关联到可信运行、受保护的构建 / 验证定义和实际 subject；无法核对的字段保持未知。要求按所选保证等级落实，不能只校验证书来自“本组织”或同一个 GitHub Actions App。

按 Architecture v0 §8 分开记录以下判断：

| 判断 | 示例 |
| --- | --- |
| Producer trust | 构建 / 扫描 / 签名身份及其生产过程是否符合所采用策略 |
| Evidence integrity | 证明、日志及关联元数据是否完整、可核对，是否存在更正或撤销 |
| Semantic coverage | 是否覆盖所需平台、组件、漏洞范围和验收命题 |
| Actual result | 检查通过、失败、错误、取消或其他实际状态 |
| Applicability | 综合 trust / integrity / coverage 与对象、规则、时效等条件得到 true / false / unknown；不以 Actual result 成功为前提 |

trust / integrity / coverage 各自保留满足、不满足或未知及其依据，不相互替代。结果显示失败不使证据自动失去适用性；若运行错误导致必要内容或覆盖缺失，记录相应缺口，不能将错误当作已完成检查。

可信、完整且适用的失败扫描可以支持拒绝；`applicable=true` 不等于通过。必需证据缺失或未知时保持未满足；适用证据冲突或失败尚未处置时，按既定规则调查，不能只挑一次绿色重跑。未采用的控制不虚报已满足，适用性排除或例外由版本化 Profile 和有权责任人明确记录。

扫描忽略项、VEX 接受规则、信任根、准入选择器及例外属于策略面，须按 v1.1 §32 审查其来源和变更。普通验证器 revision 更新不机械增加 policy epoch；若新规则使旧成功结论不足，则按 §27、§62.2 使相关旧结论失效并迁移，不能用旧绿色状态接受新要求。部署侧相应重新评估证据、授权和未执行请求，不把仓库的旧绿灯当作部署裁决。

缓存“验证已通过”与 §4 的构建缓存不同：复用须关联实际 digest / 平台、验证命题、证据身份、信任与策略 / 验证器版本、时效及撤销状态。信任撤销、策略收紧或证据失效后须重新判定；仅以 digest 为键、或仅有一个 TTL 不能证明结果仍适用。更正与撤销保留关联记录，不能覆盖历史事实。

## 7. 发布、部署准入与运行反馈

发布前固定动作、实际执行身份、目标仓库 / 环境、制品 digest、配置 revision、适用策略与证据、授权来源及有效范围。预先授权可复用，但必须覆盖本次对象与动作；有 OIDC 凭据、合并权限、维护者身份或一次环境审批，都不能自行扩大授权。隔离区上传、来源签名、生产发布与部署是不同动作；来源签名不表达“已获准部署”。

排队、审批等待和重试后，在实际副作用前重新核对授权有效性、撤销、对象、策略与适用的未处置失败。任一绑定变化先评估影响：仍被有效预授权覆盖的可以继续，超出范围的动作受阻，不机械要求重复审批，也不能沿用已失效决定。并发部署要有目标环境的写入协调与预期状态核对，以条件写入、可靠的写入权控制或等价机制将校验绑定到实际操作，阻止迟到的旧任务覆盖新状态；仅配置 concurrency 或请求取消不证明旧写入者已停止。

生产发布与候选构建测试的凭据和环境分离。签名、上传、部署沿用架构 §7.2 的 operation ID、期望对象与核对规则；未知时阻止同一逻辑副作用和冲突目标的再次写入，跨 Attempt 生效。查询须记录范围及完整性，未找到、超时或执行器死亡不能证明原请求不会迟到完成。确认未发生且不会继续产生效果、授权仍有效时，才按目标接口契约重试；幂等键也须核对作用域、请求一致性和有效期。取消要核对已注册的延后操作，部分完成分别记录，不以新操作名清空未知范围。

Kubernetes 准入是在 API 请求处理期间执行检查。ValidatingAdmissionPolicy 提供进程内 CEL 对象校验，本身不自动完成外部 Registry 的签名、SBOM 或漏洞验证；Kyverno 等工具可以提供镜像验证能力，但策略 API、身份配置、适用对象和失败行为必须按实际版本验证。选型依据是所需检查与运行约束，不只是规则“简单或复杂”。[Kubernetes VAP](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)、[Kyverno 镜像验证](https://kyverno.io/docs/policy-types/image-validating-policy/)

准入落地需要分别验证以下条件，配置存在不等于已强制执行：

- **实际拒绝**：VAP 的 Warn / Audit 只告警或留痕；仅设置 `failurePolicy: Fail` 不替代有效 binding 的 Deny 行为。参数缺失、表达式错误和匹配条件须单独验证，未匹配不自动报错。必需控制不能把参数缺失配置成静默允许。[VAP 执行语义](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/#validation-actions)
- **覆盖与防绕过**：按实际工作负载覆盖创建、更新及相关子资源，包括采用范围内的普通、init、ephemeral 容器与控制器产生的 Pod。受检查者不得通过改标签 / namespace、添加豁免、删除 binding 或改变策略来避检；策略、参数、选择器标签和管理权限均需受保护。Webhook 的 objectSelector 可被对象标签绕开，不能未经保护就充当强制边界。[Kubernetes 动态准入](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#matching-requests-objectselector)
- **最终对象与故障**：对经过 mutation 的实际镜像 / 配置核对授权和证据，包含注入的镜像；不只校验客户端最初提交的对象。验证服务、Registry 或结果缓存故障时，可以重新验证或取得仍适用的完整依据；无法满足必需条件才阻塞，不能以故障或缓存命中跳过检查。对绕过 API 准入的路径明确排除、另设控制或限制运行范围，不能报告为完整覆盖。

例外须明确对象、被豁免条件、理由、责任、补偿措施及到期 / 撤销方式；执行身份不能批准自己的越权或降低自己的门禁。应急放行单独记录为授权例外，不能回填“检查通过”或“全部满足”。先在隔离环境验证拒绝、例外及恢复路径，再按授权启用；策略升级保持旧约束或明确的受控阻塞，不以先关闭保护、稍后补回的方式迁移。

部署准入通过不证明运行健康，也不能自动追溯阻止全部已有工作负载。运行阶段仍需要按产品风险落实访问控制、网络隔离、配置与秘密管理、补丁、观测和事件响应。回退也需当前授权，并评估旧制品是否仍可接受；它是新的操作，不抹去已发生的发布。

仓库合入、制品策略通过、发布授权、部署事实、Delivery Acceptance 和后续 Evaluation 分别记录。Capability 契约决定安装验证、健康观察或使用反馈中哪些是接受的前置条件，不能用“镜像已签名”或“Pod 已启动”代替完整能力验收。

## 8. 消费项目的最小接入

先选择真实交付对象和风险，再选择控制与工具。库 / CLI 可围绕包与安装验证；容器服务增加镜像和部署证据；只有确实使用 Kubernetes 的项目才需要绑定集群准入。Python 项目可继续使用自身的 uv、ruff、pytest 入口，C++ / Rust 项目使用对应入口；这些工具组合不是共享要求。

| 接入项 | 需要明确的决定 |
| --- | --- |
| 采用范围 | 本指南固定提交 / 路径 / 摘要、适用章节、例外及接受责任；明确仍为试点还是已采用 |
| 仓库契约 | Git/GitHub 基线、集成路径、保证等级、Plan / 验证入口、可信 CI 与策略变更准入 |
| 构建与存储 | 源码和依赖解析、构建器及身份、实际平台、制品类型、Registry / 包仓库、保留与恢复 |
| 证据与规则 | subject、必需声明及其权威来源、生产链、扫描覆盖 / 时效、策略 / 验证器版本、撤销与缓存失效、VEX / 例外及失败处置责任 |
| 发布与运行 | 动作 / 身份 / 对象 / 环境的授权绑定、有效期与撤销、目标写入协调、最终准入覆盖、延后操作核对、回退与观察窗口 |
| 试点成本 | 预算、执行时间、存储与扫描成本、人工复核；质量约束下评估收益，不以工具数量计成熟度 |

消费仓库负责检查、策略及平台配置；Daedalus 解析入口、关联对象和记录判断，不复制一套中央测试逻辑。新增安全检查如何影响 Fast / Full、发布检查及等待时间，须在消费项目中明示；不能修改覆盖后仍用旧口径声称 CI 提速。elliott.page 的既有试点不因收录本指南而迁移或增加实验变量。

## 9. 实施前验收场景

以下是待执行规格，不是已运行的测试。只选择采用范围内的场景；不适用项须有明确依据，不能隐藏失败。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同一源码重新构建、tag 移动或多平台对象不符 | 识别实际 digest 与平台覆盖，旧证据不自动复用；拒绝未满足条件的对象 |
| PR head / test-merge 制品被直接用作最终集成发布 | 核对实际源码、制品与集成关联；无可接受等价依据时补验证，签名不弥补对象错误 |
| 签名有效但身份错误、subject 错误或声明类型不符 | 验证拒绝，保留具体原因；不把密码学成功直接作为策略成功 |
| 受信任 Job 为候选自填的来源 / PASS 报告签名，或报告遗漏必需项 | 不能仅凭签名满足要求；对照已接受清单与实际生产链核对，缺证保持未满足 |
| SBOM 缺失、扫描器错误 / 超时、数据库过期 | 必需要求保持未满足；不产生“无漏洞”结论 |
| 可信、完整且覆盖当前命题的失败扫描，后来有绿色重跑或 VEX | 原失败的 applicability 可以为 true；按固定规则处置失败并核对新证据和 VEX 范围，不只保留绿色记录 |
| 两种集成路径各自采用 standard，候选修改策略 / 隐藏失败 | 验证可信维护者与独立审查、原生保护及实际阻塞 / 处置；不声称自动识别所有伪造 |
| 两种集成路径各自采用 assured，核验未接入或候选伪造最终通过 | 保持阻塞，实测独立核验、策略来源与最终检查发布边界；不能降为 standard 或移除占位 |
| 发布检查已通过，但 PR 必需 Plan / Full 缺失或只有 Queue 入队绿灯 | 不能替代对应路径的仓库准入，发布还须核对获准集成来源 |
| 不可信上游产物摘要匹配，随后进入特权 Job 或共用持久 Runner | 摘要不授予执行信任；候选代码与可污染状态不能进入签名 / 发布权限边界 |
| 信任根撤销、策略收紧或 VEX 到期后，同 digest 命中旧验证缓存 | 按新决策上下文重新核对；不使用仅按 digest 缓存的旧通过放行 |
| 复制 / 清理 Registry 后，证明丢失或验证服务 / 缓存不可用 | 无适用完整依据时阻塞；缓存故障后可重新验证，恢复不能降低必需条件 |
| 审批后更换 digest / 配置 / 环境，授权过期或撤销，旧任务迟到 | 重新核对具体授权与目标状态；超出范围或冲突的动作受阻，仍在预授权内的无须重复审批 |
| 上传、签名或部署请求超时，查询未找到但原请求可能迟到 | 保留未知并限制冲突写入；换 Attempt 或幂等键不解锁，取消须核对延后动作 |
| 准入只有 Warn / Audit、参数缺失、改标签避检或删除 binding | 必需控制不能报告已启用；实际拒绝与策略管理权限分别验证，迁移不留下无保护窗口 |
| mutation 注入未获准镜像，或通过更新 / 子资源加入新容器 | 校验最终对象及实际覆盖；缺少证据或授权时拒绝，不能继承原容器的结论 |
| 豁免身份、API 外路径或旧工作负载仍运行 | 明确覆盖限制和补偿控制；授权例外不回填通过，无相应控制不宣称完整准入 |
| 部署通过但使用失败、回退目标已不符合当前策略 | 能力按契约拒绝 / 阻塞或形成运行反馈；回退不自动绕过授权和策略 |

在隔离环境先验证一条可用交付路径及其失败路径，再按批准范围接入消费仓库。记录候选、配置、平台版本、执行日志、判断与限制；文档检查通过不能替代真实平台执行。后续修订由实际缺口驱动，采用决定和运行验收分别记录。
