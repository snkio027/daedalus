## 0. 文档定位与版本边界

Git/GitHub Workflow 负责仓库变更、验证、审查、集成与发布机制，是完整工程交付系统的子系统。

> **以语义内聚的 PR 组织仓库变更，以明确候选的验证证据支持集成，在保持质量与安全要求的前提下减少等待、重复计算和人工协调。**

一个完整能力可以包含多个 PR。`main` 表示仓库集成事实；PR 合并、Release 创建与产品能力验收分别判断。能力是否可用、可维护及产生价值，还需要实际制品、使用路径和运行反馈。

本文保留 Git 日常操作与仓库控制面的原有章节编号，重点修订 §25–32 的验证生命周期及相应 Ruleset、PR、发布和效能约定。本文是已采用的规范基线；平台行为以文末官方资料及接入时实际核验为准。

### 规范词与采用关系

- **MUST**：强制要求；例外须记录适用范围、理由、责任与补偿措施。
- **SHOULD**：默认应采用；可基于项目约束记录合理例外。
- **MAY**：可选能力，不表示每个仓库都应启用。

本版基于 v1.0 Frozen，旧版原始字节 SHA-256 为 `ae53bb825f902e4814fb88840e1069966913cba9b37cad77c179258b391f773f`。依据维护者于 2026-10-24 的明确批准，v1.1 替代 v1.0，成为本工作流及 Daedalus 引用的现行规范基线；v1.0 原文作为历史版本保留。

## 1. 核心目标

一套优秀的 Git/GitHub 工作流，应同时优化以下指标：

- **Lead Time**（交付周期）
- **Review Latency**（审查耗时）
- **Merge Conflict Cost**（冲突解决成本）
- **CI Feedback Time**（门禁反馈速度）
- **Main Branch Stability**（主干稳定性）
- **Rollback Cost**（回滚成本）
- **Delivery & Recovery Cost**（交付与恢复成本）
- **Developer Cognitive Load**（开发者认知负荷）

```text
Intent ──► Implementation ──► Verification ──► Review ──► Integration ──► main

```

核心追求不是形式上的 Commit 格式完美，而是**让一个正确的变更，以尽可能低的协调成本、经过与风险相称的验证后进入 `main`。**

## 2. 十条核心原则

- **Law 1 — `main` 是唯一权威集成状态**：`main` 分支 MUST 保持可构建且随时通过 Required Quality Gate；禁止直接推送与 Force Push；禁止将 `develop`/`staging` 作为长期代码分支。
- **Law 2 — Branch 是临时 Workspace**：分支生命周期 SHOULD 尽可能短；关注点是分支发散度与变更范围，一旦分支膨胀，应优先拆解 PR。
- **Law 3 — PR 是 Atomic Change Unit**：PR 是仓库变更与集成单元；完整产品能力可以跨越多个 PR。一个 PR 对应一个清晰意图、一套验证证据、一个可独立理解的 Diff 与一次独立回滚操作。
- **Law 4 — Squash Commit 是长期历史单位**：仓库默认采用 Squash Merge，保持主干线性历史。开发过程历史（Working History）不等于永久仓库历史（Permanent History）。
- **Law 5 — Permanent History 表达 Integration Intent**：Conventional Commits 规范 SHOULD 主要约束 PR Title 与生成的 Squash Commit Subject，无需强求开发者维护每个中间 Commit 的完美规范。
- **Law 6 — Machine 验证已编码属性**：格式、Lint、编译、测试和扫描交给自动化执行；人仍需判断检查是否覆盖真实要求，结果不能证明未编码属性。
- **Law 7 — Human Review 判断未编码假设**：人类审查者专注于意图（Intent）、系统架构（Architecture）、不变量（Invariants）、失效模式（Failure Modes）与可维护性。
- **Law 8 — Quality Gate 必须 Fail-Closed**：未知状态即为不通过（`Unknown is not Success`）。仅允许显式建模的通过与跳过，任何未捕获的异常、超时、取消均拒绝合入。
- **Law 9 — Integration Ordering 不应由开发者手工承担**：队列可用且收益成立时采用强制 Merge Queue；无队列时保留候选时效和 Full 验证，Auto-merge 仅减少手动等待。
- **Law 10 — Automation 消除协调成本，但不得隐藏不确定性**：杜绝盲目重跑测试直到绿灯的掩耳盗铃行为。偶发失败（Flaky Tests）必须保留记录并治理；隔离须有风险接受、补偿覆盖和到期责任。

## 3. 推荐 Repository 生命周期

```text
Intent / Issue → Worktree → Short-lived Branch → Draft PR
                                                │
                                         Local + PR Fast
                                                ↓
                                         Ready for Review
                                                │
                                      Fast + Plan + Review
                                                ↓
                                  明确的 Integration Candidate
                                   ┌────────────┴────────────┐
                             PR-full Profile           Queue Profile
                            最新组合上 Full          Affected → 强制 Queue
                            + 分支时效要求              merge_group 上 Full
                                   └────────────┬────────────┘
                                                ↓
                                               main
                                   ┌────────────┼────────────┐
                                 制品与发布    Nightly    能力验收与反馈
```

本地验证用于快速反馈；Ready 表示提交审查，不表示已批准；审批、验证证据与操作授权各有范围。没有队列时，Auto-merge 只负责等待与执行，不产生额外的集成验证。

## 4. Git 本地基础配置

### 4.1 推荐全局配置 Profile

```bash
git config --global init.defaultBranch main
git config --global fetch.prune true
git config --global rerere.enabled true
git config --global push.autoSetupRemote true
git config --global pull.ff only
git config --global merge.conflictStyle zdiff3

```

- `init.defaultBranch`：统一新建仓库主干为 `main`。
- `fetch.prune`：同步时自动清理远程已删除分支在本地的跟踪引用。
- `rerere.enabled`：记录已人工解决过的冲突并在未来 Rebase 中自动重用。
- `push.autoSetupRemote`：在尚无 upstream 且 push 模式适用时自动建立跟踪；不会纠正已错误绑定到 `origin/main` 的新分支。教学流程仍显式首次推送。
- `pull.ff only`：禁止 `git pull` 隐式生成 Merge Commit。
- `merge.conflictStyle zdiff3`：冲突标记中显示共同祖先基线，提升冲突识别精度。

### 为什么不推荐全局配置 `pull.rebase=true`

`git pull` 会同时触发网络拉取与历史整合。更可控、更显式的方式是分步执行：

```bash
git fetch origin
git rebase origin/main

```

## 5. 日常 Git 快速检查

```bash
# 检查当前工作区与跟踪状态
git status --short --branch

# 同步远端分支与修剪失效引用
git fetch --prune origin

# 图形化查看提交拓扑
git log --graph --decorate --oneline --all --date-order

# 查看当前分支相对 main 的新增提交
git log --oneline origin/main..HEAD

# 查看当前分支相对 main 的 PR 级 Diff
git diff origin/main...HEAD

# 检查暂存区内容
git diff --cached

```

## 6. 创建工作分支

推荐显式基于 `origin/main` 建立分支：

```bash
git fetch origin
git switch --no-track -c feat/registry-validation origin/main

```

`--no-track` 避免新 feature 分支从起点自动跟踪 `origin/main`。首次推送执行 `git push --set-upstream origin HEAD`，明确建立同名远端分支；之后核对 `git branch -vv`，再使用普通 `git push`。远端和分支名称必须符合当前项目授权。

若已有分支错误跟踪主干，先确认处于正确 feature 分支，再显式首次推送并核对 upstream；不要通过改全局 `push.default` 掩盖绑定问题。[分支跟踪](https://git-scm.com/docs/git-branch)、[Worktree 的 --no-track](https://git-scm.com/docs/git-worktree)、[push.autoSetupRemote](https://git-scm.com/docs/git-config#Documentation/git-config.txt-pushautoSetupRemote)

推荐的前缀规范：`feat/*`、`fix/*`、`refactor/*`、`docs/*`、`test/*`、`chore/*`、`spike/*`。

## 7. Worktree-First 并行开发

Git Worktree 允许在同一仓库对象数据库下检出多个工作目录，减少切换成本。工作目录隔离不等于权限隔离；每个可变工作区必须有明确写入者。

```text
Workspace/
├── atlas/                      (main)
├── atlas-registry-validation/  (feat/registry-validation)
└── repo-hotfix/                (fix/critical-auth)

```

### 7.1 创建与清理 Worktree

```bash
# 创建并切换到新 feature worktree
git fetch origin
git worktree add --no-track -b feat/registry-validation ../atlas-registry-validation origin/main

# 查看当前活跃的 worktree
git worktree list

# 完成并清理
git worktree remove ../atlas-registry-validation
git worktree prune  # 清理已丢失目录的元数据

```

### 7.2 缓存与构建状态隔离原则

- **共享不可变/内容寻址缓存**：Go Build Cache、pnpm store、Cargo registry、`sccache`、`ccache`、Docker Layer Cache。
- **隔离可变构建状态**：`target/`、`dist/`、`build/`、`node_modules/` 以及本地绑定的测试端口和临时数据库。

## 8. Commit 实践

### 8.1 暂存与原子化提交

新创建的未跟踪文件需显式纳入暂存区（或通过 `git add -N` 声明 Intent-to-add），已有文件的变更通过交互式暂存拆分 Hunk：

```bash
git status --short

# 1. 新建文件显式加入暂存区（或使用 git add -N 声明意图）
git add path/to/new-file

# 2. 对已有文件按 Hunk 原子化暂存
git add -p

# 3. 校验暂存候选集
git diff --cached
git diff --cached --check

# 4. 提交
git commit -m "refactor: isolate registry inventory"

```

### 8.2 允许过程性临时提交

在 Squash-Only 架构下，分支上的 `wip`、`fix test`、`address review` 不会进入 `main` 分支。无需过度执行本地 `rebase -i` 或频繁 `amend`。

## 9. Rebase 触发时机

不要无目的地频繁 Rebase。仅在以下场景主动 Rebase：

1. `main` 分支发生影响当前模块的结构性变更；
2. 即将准备处理显式冲突；
3. PR 生命周期较长需要确认最新集成状态；
4. 整理 Stacked PR 依赖拓扑。

```bash
git fetch origin
git rebase origin/main

```

## 10. 重写已 Push 分支的安全策略

重写本地历史后推送至个人特性分支时，MUST 使用：

```bash
git push --force-with-lease

```

`--force-with-lease` 核对预期远端状态；默认预期来自本地跟踪 ref。存在后台 fetch 时，SHOULD 记录已审核的远端 SHA 并使用显式 lease，不能假设该参数保证绝不覆盖未见修改。[Git 官方说明](https://git-scm.com/docs/git-push#Documentation/git-push.txt---force-with-lease)

## 11. PR Title 规范

PR Title MUST 遵循 Conventional Commits 规范，作为生成最终 Commit 与 Release Notes 的核心依据：

- `feat(registry): validate node inventory atomically`
- `fix(ci): fail closed when heavy tests are cancelled`
- `refactor(bootstrap): separate artifact resolution`
- `docs(workflow): define merge queue policy`
- `chore(actions): pin checkout to immutable SHA`
- `feat(api)!: replace authentication contract`（Breaking Change）

## 12. Squash History 契约

在 GitHub 仓库设置中，MUST 配置：

- **Allow squash merging**: `Enabled`
- **Allow rebase merging**: `Disabled`
- **Allow merge commits**: `Disabled`
- **Default commit message**: **`Pull request title`**（推荐）或严格格式化后的 `Pull request title and description`。

> ⚠️ **严禁选择 `Pull request commit details`**，防止将开发分支中未整理的过程性 commit log 串联注入主干。

## 14. 推荐 PR Template

`.github/pull_request_template.md` 保持简短，记录实际证据，避免把未运行检查预填成通过：

```markdown
## Why

问题、使用场景，以及关联 Capability / Issue。

## What

变更后的行为、关键取舍和非目标。

## Validation

- 候选：PR head SHA；实际受测 SHA / tree；采用的验证 Profile。
- 已运行：命令或 CI run 链接、环境、覆盖范围、实际结果。
- 未运行 / 不适用：项目、理由、采用的规则，以及在哪个边界补齐。
- Affected 计划：比较范围、受影响组件、是否回退 Full、计划记录链接。
- 集成证据：Full run 对应的 PR test-merge 或 merge-group SHA（未产生则写待运行）。

## Risk & Rollback

风险、兼容性影响、回滚或恢复方式；高风险操作的授权边界。

## Notes for Reviewers

需要判断的不变量、失败模式和测试覆盖；能力验收尚缺什么。
```

Fast 通过不能填写为 Full 通过；`skipped`、未知和失败分别记录。PR 描述是证据导航，不替代 CI 事实；同一 PR 更新后需要重新判断旧证据适用性。

## 15. PR 大小：Semantic Cohesion > LOC

不采用死板的 LOC 硬门禁，而以语义内聚性（Semantic Cohesion）作为第一准则：

> **One PR = One independently understandable and reversible change.**

- `~200–400 LOC`：通常极易理解与审查。
- `~800+ LOC`：应主动检查是否包含可拆解的重构或独立层级。
- `~1500+ LOC`：通常代表架构拆分不合理，除非大部分为自动生成的 Schema 或快照。

## 16. Author Self-Review 流程

请求 Review 前，作者 SHOULD 检查完整 PR diff，并运行适用的本地快速与受影响验证；昂贵检查按集成 Profile 安排，不要求每个中间提交都全量运行。

```bash
git fetch origin
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD
git diff --check origin/main...HEAD
task quality:fast
export CI_PLAN_PATH="$(mktemp "${TMPDIR:-/tmp}/quality-plan.XXXXXX")"
task quality:plan
task quality:affected  # 比较范围及失败回退须满足 §31
```

Ready 后使用 `gh pr checks --required --watch --fail-fast` 观察当前候选。应核对对应 run、事件及受测对象，而不是只看绿色名称；本地通过不能替代 Required Check。

### Git Diff Check 的三个 Scope

- `git diff --check`：未暂存修改。
- `git diff --cached --check`：已暂存候选。
- `git diff --check origin/main...HEAD`：完整已提交 PR 差异。

未跟踪文件必须另外纳入检查。存在未提交修改的本地结果不能冒充对干净提交的验证。

## 17. 转换为 Ready for Review

```bash
gh pr ready
```

Ready 转换 MUST 触发所需验证，即使没有新 commit。§28 显式监听 `ready_for_review`；退回 Draft 后停止过时的昂贵运行，下一次 Ready 再检查。标签和作者自述不能替代受测对象与有效门禁。

## 18. Reviewer 审查优先级

```text
1. Intent (意图与合理性)
      ↓
2. Architecture (架构边界与依赖)
      ↓
3. Invariants & Correctness (正确性与不变量)
      ↓
4. Failure Modes & Edge Cases (失效模式与异常)
      ↓
5. Tests & Evidence (测试充分度与覆盖)
      ↓
6. Maintainability (可维护性)
      ↓
7. Style / Naming (风格与命名)

```

---

## 19. Review 批注严重级别约定

- `blocking:` 必须修复后方可合并（如并发竞争、内存泄露、架构违规）。
- `question:` 存在疑问，需要作者澄清，但不一定需要改动代码。
- `suggestion:` 优化建议，作者可自行评估是否采纳。
- `nit:` 细微风格建议，不阻塞合入。

## 21. CODEOWNERS 策略

`.github/CODEOWNERS` 应该用来保护**关键控制面边界**，而不是制造全量审批瓶颈：

```text
/.github/                    @platform-team
/Taskfile.yml                @platform-team
/scripts/quality/            @platform-team
/scripts/ci/                 @platform-team
/ci/                         @platform-team
/security/                   @security-team
/bootstrap/                  @platform-team

```

> 将 `/.github/` 纳入所有权范围，使 `.github/CODEOWNERS` 自身也接受所有权审查；只有实际启用必需 Code Owner Review、有效所有者和相应分支规则时，才构成强制约束。

## 22. main 分支 Ruleset 与集成 Profile

共同要求：PR-only、禁止 Force Push 和删除主干；配置所需审查、对话解决与策略面 Code Owner Review；默认 Squash 与线性历史。Required Check 使用实际观测到、含 Profile 与策略代次的 check context，例如 `Delivery / Quality / pr-full-standard-v1`，并绑定预期生产者。同名检查不能来自无关 workflow；GitHub App 身份相同也不能替代对具体 workflow 的保护。普通成员、自动化身份与管理员的日常操作都不得享有绕过；必须核对 Ruleset 的实际生效状态和 bypass 列表，而不只是规则名称。

仓库 MUST 选择并记录一个集成 Profile：

| Profile | 适用条件 | 合入前必需验证 | 平台约束 |
| --- | --- | --- | --- |
| **PR-full（默认）** | 无可用队列、未强制队列，或当前规模不值得使用队列 | Ready PR 生成 Affected 计划，最新有效 test-merge 候选执行 Fast + Full；由 Full 覆盖计划要求 | Required Checks 加分支 up-to-date 要求；main 变化后更新分支并重验适用候选；Auto-merge 不能豁免 |
| **Queue** | 已核验可用性并强制所有正常合入经过 Merge Queue | Ready PR 生成计划并执行 Fast + Affected（必要时升级 Full）准入队列；merge-group 执行 Fast + Full | Require merge queue；队列同样要求聚合检查；关闭日常 bypass |

截至本次核验，GitHub 官方列出的 Merge Queue 可用范围是组织拥有的公开仓库，以及 Enterprise Cloud 组织的私有仓库；不能因个人仓库公开就假设它支持队列。实际账户与目标分支配置仍须核验。[官方可用范围与配置](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

没有 Code Owner / Ruleset 等能力或没有可用独立审查者时，记录限制和替代责任，不把“文档要求”报告成“已强制执行”。个人作者不能给自己的 PR 制造独立批准。仓库还须独立选择 §26.2 的保证等级：常规协作可以在可信人工审查和有效保护规则下使用 Auto-merge / Queue；高保证准入必须先落实 §26.3，不能以常规检查冒充独立核验。

**只添加 `merge_group` 触发器，不等于启用了强制队列。** 未满足 Queue 前置条件时保留 PR-full，不能让 Fast 成为直接合入的唯一验证。

## 25. Repository-Owned Quality Logic 与验证层级

验证逻辑由消费仓库单一维护；CI 调度事件、环境与资源，调用仓库入口并保留结果。把“决定检查范围”和“执行检查”分开，避免计划阶段触发额外一轮 Full。

| 层级 / 入口 | 职责 | 运行边界 |
| --- | --- | --- |
| Fast / `quality:fast` | 格式、Lint、轻量编译 / 类型检查、便宜单测 | 开发循环；Draft / Ready PR 和集成组合的早期反馈 |
| Plan / `quality:plan` | 生成候选、比较范围、检查 / 环境清单、理由及 Full 回退标志；不执行测试 | Ready PR；本地按需；未知范围生成合法 Full 计划或失败 |
| Affected / `quality:affected` | 读取并校验计划，执行受影响检查；Full 计划则升级为一次 Full | Queue 的 Ready PR；本地按需 |
| Full / `quality:full` | 执行当前集成契约完整检查，并满足同候选 Affected 计划要求 | PR-full 的 Ready PR；merge-group；Affected 升级时 |
| Extended / `quality:extended` | 额外兼容组合、长时压力、探索性性能与扩展安全检测 | Nightly / 手动诊断；发布前按契约补齐 |

PR-full 的 Ready PR 采用 `Plan → Full`，不另起一个执行 Affected / 回退 Full 的 Job。Full 必须覆盖该计划的 check ID、环境和构建选项；覆盖不全时补齐后才可通过，不能仅将 Affected 标为 skipped。

Full 表示“当前集成契约要求齐全”，不等于穷举一切；真实支持平台和风险决定检查集合。merge-group 从完整集成契约运行 Full，不依赖单个 PR 的选择计划推断组合覆盖。Linux 结果不能代替 macOS；不同 sanitizer、ABI、feature flag 和工具链组合分别验证。

执行器按候选、输入、check ID、环境和构建选项去重。Fast 与 Full 内部重叠的检查也可以复用同一对象的明确结果，或使用互补清单与汇总校验，但不能因此使 Full 脱离其完整覆盖承诺。§28 仅消除独立 Affected / Full 的重复执行，仍保留单独 Fast，未实现跨 Job 构建与结果复用；这部分成本须继续测量。

兼容入口 `task quality` SHOULD 映射为 `quality:full`，不把无参数入口悄悄变轻；本地没有 CI 计划时，Full 按完整契约运行。已有 `quality:heavy` 的迁移须核对覆盖后再弃用。

Local 10–30 秒、PR p95 三分钟仅是初始目标。预算按项目实测调整，不能为达标删除必需验证。**PR-full 中每次 Ready PR 更新仍需要当前候选的 Full；本轮首先减少 Draft 和重复计算，不自动消除所有 Ready 等待。**

## 26. 规则、证据与准入的边界

### 26.1 证据必须回答的命题

```text
Repository Policy / Profile → 仓库验证入口
                                      ↓
                         可信 CI 运行与验证证据
                                      ↓
                          核验后发布版本化 Quality context
                                      ↓
                         Ruleset 强制执行合流准入
```

CI 是仓库 Required Check 的受信任生产系统；本地实验、独立测试平台、人工判断和运行观测可以支持其他命题，不能冒充 Required Check。只有身份可信、结果完整、覆盖匹配且对象适用的证据，才可支撑当前判断。可信失败仍然支持拒绝，检查无失败不证明全部产品质量。

每次运行至少记录：event、PR head（若适用）、base、实际 checkout SHA / tree、集成 Profile / 保证等级 / policy epoch / 验证器版本、环境 / 工具链、受影响计划及理由、必需检查集合、各项结果、日志 / 制品和 run ID / attempt。缓存命中、Job 退出码和模型总结不单独构成验收依据。

PR head、PR test-merge、merge-group 和最终 main 提交可能不同；不得混称“PR SHA”。`pull_request` 默认验证合并 ref，`merge_group` 使用组合候选；记录实际 checkout 对象，并将最终集成提交关联回它。不得从 PR head 重新 checkout 覆盖 merge-group 候选。[事件与 SHA 定义](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

候选、base、规则、环境或制品改变时重新评估证据。复用需要明确等价依据；不允许把旧绿色状态复制到新 SHA。Required Checks 对最新候选的要求、head 与 test-merge 的区别见[官方说明](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)。

### 26.2 保证等级：独立于集成方式

集成方式决定候选如何进入 main；保证等级决定依赖哪些信任假设，以及哪些责任由机器强制。两者分别记录：`PR-full / Queue × standard / assured`。

| 保证等级 | 信任假设 | 接入要求与边界 |
| --- | --- | --- |
| **常规协作基线（standard）** | 维护者和独立审查者可信，负责审核策略修改、测试覆盖及失败处置 | 必需检查、明确候选、策略文件审查、最小权限、完整运行日志、有效审查与受控合入；可使用原生 Auto-merge / Queue，不要求先自建独立准入系统 |
| **高保证准入（assured）** | 需要防范候选改写验证器、伪造通过，或在较高自治程度下减少人工裁决 | 在常规基线上落实 §26.3 的独立策略来源、核验 / 发布边界和适用失败记录；接入前保持阻塞，执行相应反例验收 |

按威胁模型、自治范围和失败后果选择，不按个人 / 团队规模机械划分。PR-full 可以采用 assured，Queue 不自动获得 assured。standard 依赖可信审查者守住策略与失败治理，不声称原生状态检查能够独立识别所有伪造证据；缺少此信任前提时，应补齐控制或明确受控例外，不能假定 standard 已满足。

保证等级选择及变更由有权维护者接受，不能由候选切换一个环境变量来自行降低要求。[GitHub 原生保护能力](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

### 26.3 高保证准入的核验接口

`needs.*.result == success` 只证明所列 Job 返回成功；不能证明检查确实执行、覆盖齐全、生产者可信或历史失败已处置。采用 assured 的仓库 MUST 为最终门禁绑定以下输入和核验责任，不能只增加一个由候选自行填写的 `trusted=true`：

| 输入 | 核验条件与权威来源 |
| --- | --- |
| 已接受策略 | 固定 Profile、policy epoch、目标分支、检查集合 / matrix、验证器 revision / digest；由维护者控制的策略来源提供，不从候选任意改写的计划反推要求 |
| 当前候选 | 仓库、PR / merge-group、head、base、实际 test SHA / tree、当前 Ready / 队列状态；从平台与实际 checkout 记录核对，事件快照不能冒充实时状态 |
| 生产者与运行 | 允许的 App、workflow 路径及实际 workflow revision、event、run ID / attempt、Runner / 工具链；同 App 的无关 workflow 不可替代 |
| 覆盖与完整性 | 按稳定 check ID 与环境组合对照 required manifest 和实际结果；缺项、重复矛盾、报告缺失、下载失败、摘要不符都拒绝；候选报告只是待核对输入 |
| 结果与失败处置 | 必需项成功，合法空计划有规则依据；核对适用的未解决失败、重跑、隔离决定及其有效期（§42），不是只读最后一次结果 |
| 准入决定 | 记录以上输入的版本、引用与判断；未知或不适用时拒绝；发布 check 的身份与候选执行身份隔离，且发布前重新核对当前候选和策略 |

失败运行也须保存报告与日志；取消导致来不及上传时记录缺证，不能补写通过。读取报告只作为数据处理，不在持有发布凭据的上下文执行候选脚本或报告中的命令。

记录格式由仓库选择，JSON 文件加平台运行记录即可作为起点，不要求新建数据库。每份报告应能定位 `policy_epoch / candidate / check_id / environment / result / run_id / attempt / artifacts`；检查清单来自已接受策略，不能把实际产出的清单直接当成必需清单。报告存在和摘要正确也不证明其测试语义正确，仍须审查验证器与测试覆盖。

执行边界可采用独立 GitHub App，或由维护者控制、固定来源的验证 / 发布 workflow。后者必须证明候选不能更换来源、直接发同名通过结果或在发布上下文执行候选代码；只固定 reusable workflow 的 SHA，而允许调用方随意替换，并不构成强制边界。组织级 Required Workflow 可能提供部分约束，但须核验套餐、来源与事件差异（§30）。普通 Required Status Check 的 App 绑定不能区分同一个 GitHub Actions App 内的所有 workflow。

在 assured 下，先跑通“报告生成 → 独立核对 → 版本化检查发布 → Ruleset 拒绝缺项”，再开放该等级的自动准入。外部发布者接管检查时，骨架 Job 改为不同的阶段反馈名称，最终 Required Check 只有一个受信任生产者。未接入时保留 §28.3 的阻塞步骤；删掉阻塞或替换成 `echo` 不构成接入，也不能静默降为 standard。

## 27. 策略身份与聚合门禁的阶段语义

检查身份可采用 `Delivery / Quality / <integration>-<assurance>-<epoch>`，例如 `pr-full-standard-v1`、`queue-standard-v1` 或 `pr-full-assured-v1`；实际 context 从真实 run 核验。一个 context 在同一接受契约内稳定，避免把含义不同的旧绿灯用于新规则。

**验证器 revision 标识执行了什么；policy epoch 标识哪些成功结论仍可接受。** 每次验证器 / 测试更新记录 revision，但不机械增加 epoch 或暂停全仓库。

| 变化 | 处置 |
| --- | --- |
| 普通回归测试、诊断信息或内部重构；旧结论仍满足当前接受契约 | 记录新 revision，正常审查并验证新候选；不自动更换 Required Check 或进入维护窗口 |
| Queue → PR-full、最终生产者 / 保证等级改变、提高要求导致旧绿灯不足 | 新 context / epoch，按 §62.2 使旧证据失效并迁移 |
| 新发现高风险使某项新增检查成为所有待合入候选的前置条件 | 即使只新增一个测试，也要重新评估开放候选；不能以“普通测试更新”为由沿用不足的绿灯 |

判断依据是旧结论是否仍被允许接受，而不是文件是否发生修改。若不采用改名，应提供同等可验证的旧证据失效机制；仅更新 YAML 变量不具备这个效果。

下表描述必要阶段条件；常规协作还依赖 §26.2 的可信审查，高保证还要求 §26.3 的独立核验。`MODE` 表示执行入口；Queue 的 `affected` 入口允许根据计划升级 Full，并记录实际覆盖。

| 上下文 | Fast | Plan | Validation / Execution | MODE | 聚合成功的范围 |
| --- | --- | --- | --- | --- | --- |
| Draft PR | success | 未执行 | skipped | 无 | 不产生准入成功 |
| Ready PR / PR-full | success | success | success | full | Full 覆盖计划后满足本阶段检查；不另跑 Affected |
| Ready PR / Queue | success | success | success | affected | 按计划执行 Affected 或升级 Full，只支持入队 |
| merge-group / 任一 Profile | success | skipped | success | full | 满足组合检查；PR-full 下仅用于受控迁移或诊断 |
| 未知 event、Profile、模式或缺失结果 | 任意 | 任意 | 任意 | 任意 | 拒绝 |

PR-full 没有独立 Affected Job，**其要求仍由成功生成的计划和 Full 覆盖满足**。选择器确认无相关测试时输出可核对的空计划及理由，必要文档检查仍执行。只有 merge-group 的 PR 选择计划允许 skipped，因为该阶段执行完整集成契约。

GitHub 可能把 skipped / neutral 当作满足 Required Check；聚合须自身运行并核对必需依赖，不能用条件跳过代替判断。失败、取消、超时、必需项缺失均不能视为通过。[Required Check 行为](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

## 28. GitHub Actions 流水线与 Profile 切换

### 28.1 常规协作基线：PR-full 示例

这是 standard 等级的接入骨架。仓库须实现 `bootstrap`、`quality:fast / plan / full`、报告保存和所需平台覆盖；采用 Queue 或本地 Affected 路径时再实现 `quality:affected`，PR-full 试点不要求另建该入口。它不是开箱即用的通用 CI。Plan 与执行共享一次 checkout / bootstrap；PR-full 中不启动第二份 Affected / Full。超时参数待实测，`ubuntu-latest` 不是不可变环境。

`quality:plan` 写入 `CI_PLAN_PATH`，不执行测试。PR 事件中的 `quality:full` / `quality:affected` 必须解析、校验并消费同一计划，拒绝对象不符、缺项或非法格式；文件非空检查不能替代这些职责。PR-full 的 Full 核对计划要求均已覆盖，merge-group 的 Full 不要求 PR 计划，独立使用完整集成契约。失败时也须保留计划和日志；报告上传 / 保留由项目补齐，不得把下面的 Job 成功等同于独立证据保证。

```yaml
name: Delivery

on:
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened, edited, ready_for_review, converted_to_draft]
  merge_group:
    types: [checks_requested]
    branches: [main]

permissions:
  contents: read

env:
  INTEGRATION_PROFILE: pr-full

concurrency:
  group: ${{ github.workflow }}-${{ github.event_name }}-${{ github.event.pull_request.number || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  fast:
    name: Fast
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          ref: ${{ github.sha }}
          persist-credentials: false
      - run: ./scripts/ci/bootstrap
      - run: task quality:fast

  validate:
    name: Plan and validate
    if: ${{ github.event_name == 'merge_group' || (github.event_name == 'pull_request' && github.event.pull_request.draft == false) }}
    runs-on: ubuntu-latest
    timeout-minutes: 60
    outputs:
      plan_result: ${{ steps.plan.outcome }}
      execution_result: ${{ steps.execute.outcome }}
      mode: ${{ steps.mode.outputs.value }}
    env:
      CI_EVENT: ${{ github.event_name }}
      CI_BASE_SHA: ${{ github.event.pull_request.base.sha || github.event.merge_group.base_sha }}
      CI_HEAD_SHA: ${{ github.event.pull_request.head.sha }}
      CI_TEST_SHA: ${{ github.sha }}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          ref: ${{ github.sha }}
          fetch-depth: 0
          persist-credentials: false
      - run: ./scripts/ci/bootstrap
      - name: Select execution mode
        id: mode
        shell: bash
        run: |
          set -euo pipefail
          case "$INTEGRATION_PROFILE:$CI_EVENT" in
            pr-full:pull_request|pr-full:merge_group|queue:merge_group) mode=full ;;
            queue:pull_request) mode=affected ;;
            *) echo "Unknown profile or event"; exit 1 ;;
          esac
          echo "value=$mode" >> "$GITHUB_OUTPUT"
      - name: Plan affected coverage without running tests
        id: plan
        if: ${{ github.event_name == 'pull_request' }}
        env:
          CI_PLAN_PATH: ${{ runner.temp }}/quality-plan.json
        shell: bash
        run: |
          set -euo pipefail
          task quality:plan
          test -s "$CI_PLAN_PATH"
      - name: Execute selected validation once
        id: execute
        env:
          CI_PLAN_PATH: ${{ runner.temp }}/quality-plan.json
          VALIDATION_MODE: ${{ steps.mode.outputs.value }}
        shell: bash
        run: |
          set -euo pipefail
          case "$VALIDATION_MODE" in
            full) task quality:full ;;
            affected) task quality:affected ;;
            *) echo "Missing or invalid execution mode"; exit 1 ;;
          esac

  quality:
    name: Delivery / Quality / pr-full-standard-v1
    needs: [fast, validate]
    if: ${{ always() }}
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Evaluate phase policy
        env:
          EVENT: ${{ github.event_name }}
          BASE_REF: ${{ github.event.pull_request.base.ref || github.event.merge_group.base_ref }}
          PR_STATE: ${{ toJSON(github.event.pull_request.draft) }}
          FAST: ${{ needs.fast.result }}
          VALIDATE: ${{ needs.validate.result }}
          PLAN: ${{ needs.validate.outputs.plan_result }}
          EXECUTION: ${{ needs.validate.outputs.execution_result }}
          MODE: ${{ needs.validate.outputs.mode }}
        shell: bash
        run: |
          set -euo pipefail
          require_result() {
            if [[ "$2" != "$3" ]]; then
              echo "$1: expected $3, got $2"
              exit 1
            fi
          }
          case "$INTEGRATION_PROFILE" in
            pr-full|queue) ;;
            *) echo "Unknown integration profile"; exit 1 ;;
          esac
          require_result Fast "$FAST" success
          require_result Validation "$VALIDATE" success
          require_result Execution "$EXECUTION" success
          case "$EVENT" in
            pull_request)
              require_result Base "$BASE_REF" main
              require_result Ready "$PR_STATE" false
              require_result Plan "$PLAN" success
              case "$INTEGRATION_PROFILE" in
                pr-full) require_result Mode "$MODE" full ;;
                queue) require_result Mode "$MODE" affected ;;
              esac
              ;;
            merge_group)
              require_result Base "$BASE_REF" refs/heads/main
              require_result Plan "$PLAN" skipped
              require_result Mode "$MODE" full
              ;;
            *) echo "Unexpected event: $EVENT"; exit 1 ;;
          esac
          echo "Standard phase checks passed; review and repository admission still apply."
```

Draft 的 Fast 可以变绿，最终聚合明确不准入；转 Ready 后重新运行 Plan 和验证。`always()` 仅用于短小汇总，不保证整次取消后一定执行；必需步骤禁止 `continue-on-error`。standard 的绿色结果仍需有效审查和仓库保护，不意味着已实施 §26.3。

### 28.2 常规协作基线：Queue 差异

只有按 §62.2 完成受控迁移并使强制队列生效，才采用以下配套差异：

```diff
 env:
-  INTEGRATION_PROFILE: pr-full
+  INTEGRATION_PROFILE: queue
 jobs:
   quality:
-    name: Delivery / Quality / pr-full-standard-v1
+    name: Delivery / Quality / queue-standard-v1
```

执行模式从 Profile 和 event 推导：Ready PR 为 Plan → Affected（必要时一次 Full），merge-group 为 Full；无需维护两套 Full 条件。模式输出缺失或不符会被拒绝，但 Bash 不能检测 Ruleset 是否真的强制队列，须由平台验收保证。PR green 只支持入队，组内 green 才支持组合准入。

### 28.3 高保证准入：必须保留的接入阻塞

采用 assured 时，在对应 PR-full / Queue 骨架上选用新的 assured context，例如 `Delivery / Quality / pr-full-assured-v1`，并在 `quality.steps` 最后追加以下步骤，直至 §26.3 的真实独立核验接入并验收：

```yaml
- name: Block until trusted evidence admission is bound
  shell: bash
  run: |
    echo "Assured admission is not configured; bind section 26.3 before enabling it."
    exit 1
```

这是**高保证接入占位**，不是常规协作默认配置。不得为了绿灯删除它；替换时必须核验最终检查生产者及防篡改边界，不能只换成一个候选可控制的成功命令。已选择 assured 的项目若需要改成 standard，必须显式接受信任边界变化并迁移。

### 28.4 默认触发与待优化调度

骨架保留 `edited`，以保守覆盖更换目标分支；标题 / 描述变化也会重跑，并可能取消正在执行的 Full。**这一成本尚未优化，必须计入 §61 的取消 / 重跑测量。** base 改变后必须验证新 test-merge，不能沿用旧目标结果。up-to-date 不保证 main 更新就自动触发每个 PR workflow；无队列时需更新分支并重验。

后续可将标题 / 描述校验放到独立 metadata workflow 和并发组，代码验证仅处理候选或 base 变化。实施前须实测 `edited` 的 base 变更识别、当前对象、重触发与权限；单纯移除 `edited` 会漏验证，而让同名必需聚合在 metadata-only run 中 skipped 可能错误满足门禁。元数据检查不能取消代码 Full，也不能发布代码准入绿灯。本文未提供或部署该调度优化。

feature branch 使用 PR 检查；主干 `push`、Nightly、手动诊断采用独立名称和目的。普通 `workflow_dispatch` 的 Job 成功不自动满足 PR Required Check，不能用“手动跑绿后改标签”代替合格事件证据。[事件与 activity types](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)、[检查事件限制](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

## 29. CI Concurrency、缓存与计算成本

PR 按 workflow + event + PR number 分组，后启动的运行可以取消同组运行；这不保证按提交先后排序。重跑旧 run 可能反而取消新候选运行，因此准入必须核对当前候选，必要时重新触发当前候选，不能把最后完成的 run 当成最新证据。merge-group 按 run ID 隔离，排序与并发由 Merge Queue 管理。只设 `cancel-in-progress: false` 不足以保护共享组中的 pending runs：默认同组新 pending 会替换旧 pending，不能把所有 merge-group 放进一个固定组。[Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

优化次序 SHOULD 是消除重复触发、按覆盖选择工作、复用构建与缓存、再调整 Runner 和并发；每一步检查质量及总成本，而非只追求单个 Job 更快。

- **构建复用**：能共享同一候选、编译选项与环境的制品时 Build Once → 多类测试；记录构建来源、digest 和工具链。不同 ABI、sanitizer、feature flag 或平台不得混用同一二进制。上传 / 下载成本超过重复构建时据测量调整。
- **缓存键**：包含影响内容的 OS、架构、工具链、lockfile、构建选项和相关版本；依赖缓存与可变工作区状态分开。命中缓存后仍运行应执行的验证，不能缓存“通过结论”。
- **信任隔离**：缓存中不得包含 secrets；特权发布不得消费不可信 PR 可污染的缓存 / 制品并执行其内容。缓存不是验收证据或发布制品。
- **访问范围**：PR merge-ref 缓存的复用范围受限；符合条件时可读默认分支缓存。可评估受信任主干预热，但不得承诺 sibling PR 总能共享。[缓存范围与安全](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)

Rust 可测量 registry / 编译缓存，C++ 可测量依赖缓存与 ccache / sccache，Go 可测量模块 / 构建缓存；不得不加区分地跨候选共享整个可变 `target/` 或 `build/`。

## 30. 必需检查工作流与 Matrix 的边界

本文的“产生 Required Check 的 workflow”不等于组织 / 企业 Ruleset 的 **Required Workflow** 功能。后者具有独立的来源、适用套餐和事件限制；官方说明其忽略 `branches / paths / types` 过滤，仅按默认 activity types 触发，不能把 §28 的 Draft / Ready / edited 行为直接套过去。采用该功能须单独设计事件补齐并实测，且不能沿用 §28 的 `cancel-in-progress` 配置；普通 workflow 加 Required Check 的配置也不自动获得它的来源约束。[Required Workflow 限制](https://docs.github.com/en/enterprise-cloud%40latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules)

产生 Required Check 的普通 workflow 不使用顶层 path / commit-message 过滤来选择检查；选择工作放到内部，聚合 context 对所有目标候选稳定出现。Job 跳过与 workflow 未触发不同，后者可能让 Required Check 持续 pending。[官方跳过行为](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

平台、编译器、sanitizer、性能和安全测试按**风险与验收契约**分层：

- 每次 PR push 保留快速反馈；影响某个平台或安全边界的修改可以提前运行专项验证。
- 合入必需的支持平台、关键兼容性、性能阈值和安全检查 MUST 包含在 Full，不因昂贵移到 nightly。
- 额外兼容组合、长期压力或扩展检查可放 Extended；项目明确延迟发现的风险、责任和最大处置时间。Nightly 失败关联实际 main SHA，阻止受影响发布并形成修复决定，不能用“已合并”关闭问题。
- Release 契约要求的检查在发布前对对应制品补齐；nightly 旧版本通过不自动覆盖新制品。定时任务可能延迟或未运行，发布必须检查所需证据是否真实存在。

Matrix 的 `fail-fast: true` 可减少无效运行，但被取消的组合是未验证，不能当作全部通过；需要保留全部平台诊断时可设 false。是否允许非阻塞 experimental 组合必须在规则中单独声明，不能用于隐藏必需失败。[Matrix 语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstrategyfail-fast)

## 31. Affected Validation 的保守选择契约

Affected 不是简单的 `paths:` 匹配，而是：

```text
固定 base / head / test SHA
        ↓
完整 changed-file 集合（含删除、重命名旧新路径）
        ↓
组件与依赖映射 → 反向依赖闭包 → 必需检查及环境
        ↓
Plan：记录计划与理由（不运行测试）
        ↓
Execution：校验计划 → 执行所需检查 → 记录实际覆盖与结果
```

PR 中用固定 base / head 的 merge-base 得到作者变更范围，并在实际 test-merge 候选上执行。选择器必须核对提交对象与关系，不使用执行时漂移的 `origin/main` 代替事件基线。本地模式须显式处理未暂存、暂存与未跟踪文件，或要求干净工作树；不允许漏掉本地修改却报告空变更。项目实现须规定本地比较基线及计划格式；§16 / §47 通过同一个 `CI_PLAN_PATH` 传递计划，不代表已经提供这些入口。

| 情况 | 必需行为 |
| --- | --- |
| 普通组件修改 | 覆盖该组件、反向依赖与受影响契约 / 使用路径 |
| 删除、重命名、生成源或共享配置修改 | 同时分析旧新路径及生成关系；不能只看剩余文件 |
| lockfile、工具链、根构建、CI / 策略 / 选择器变化 | 默认 Full，或由受保护规则给出可复核的同等覆盖依据 |
| diff 截断 / API 未完整分页 / 历史缺失 / 未知路径 / 图不完整 | 保守回退 Full；无法运行 Full 时失败，不输出“无需测试” |
| 确认没有受影响测试 | 选择器成功，输出空计划、适用规则与理由；必要文档检查仍执行 |
| 选择器报错、计划缺失或格式非法 | 失败；不得将损坏的计划解释为无需验证 |

`quality:plan` MUST 保存候选 SHA、比较范围、图 / 规则 revision、检查与环境清单、`full_required`、理由。`full_required` 只允许明确的布尔值；未知范围应输出 `true` 的合法计划，输出缺失 / 非法则失败。不能调用后续 Full 来掩盖计划生成失败。计划阶段不调用 Full。

执行入口读取同一计划并记录实际结果。PR-full 的 Full 校验计划要求是本次成功覆盖的子集；Queue 的 Affected 在 `full_required=true` 时直接升级为一次 Full，不先执行 Affected 再重复整套 Full。必需检查全部完成才退出 0；失败不能被后续回退或重复执行的绿灯抹掉。计划和执行分离是职责分离，不要求单独的 Job、服务或数据库。

在选择算法未证明稳定前可以让 Affected 保守执行 Full。先在一组代表性改动中与完整检查对照，追踪漏选与误选，再扩大优化范围。Queue 的 Full 不依赖 Affected 推断覆盖完整集成组合。

若实现采用 `required=true/false` Job 输出，聚合 MUST 显式解析两种合法值；空值、拼写错误和 unknown 都拒绝。禁止 `if true else allow skipped`，旧版示例中的宽松 else 不能继续沿用。

## 32. 质量策略与选择器防篡改

`.github/workflows/**`、CODEOWNERS、Taskfile、bootstrap、质量脚本、`scripts/ci/**`、依赖图 / 受影响映射、例外列表和验证 Profile 都属于 Policy Surface。MUST 对这些文件及其生成来源实施所有权审查，保护控制代码本身。

CODEOWNERS 只有结合相应审查规则才构成约束，不能阻止候选 workflow 在评审前运行。两种等级都不允许候选私自降低接受自身的条件；standard 依赖可信维护者 / 独立审查者审查策略文件、计划和覆盖，不能宣称只读 Token 或同名检查能够阻止所有 `exit 0` 伪造。

assured 另须按 §26.3 隔离独立策略、核验和检查发布身份，并测试候选替换验证器 / 伪造同名结果的拒绝路径。所有等级的候选 Job 均不持有 Ruleset 管理或生产发布凭据；assured 的候选还不能掌握最终准入发布能力。策略更新记录旧新覆盖、信任边界和证据失效判断，普通测试 revision 变更不自动触发全仓库迁移（§27）。

更改 Queue / PR-full Profile 或 Required Check 是控制系统迁移，不是普通成本调优开关。具体步骤及失败案例见 §62。

## 37. Auto-merge 的职责

```bash
gh pr merge --squash --auto
```

在有效授权内登记 Auto-merge，平台等待保护条件后执行。它不重新验证合并后的组合，也不代替 up-to-date / Queue 规则。无队列默认 PR-full；新提交或 base 改变后，旧 Full 不能自动支持新候选。

## 38. 选择 Merge Queue 的条件

先核验仓库类型与套餐可用性，再评估合流竞争、Full 时长、main 更新频率、队列剔除与人工同步成本。能力不可用时采用 PR-full，不能把缺少队列解释为省略集成验证的理由。

Queue 可以把昂贵的必需验证集中在集成候选上，但一个 PR 可能因前序变化、失败或重建产生多次 merge-group。`多次 Fast + 一次 Full` 是理想化成本示例，不是运行次数承诺。选择队列还应衡量组合重建、排队等待与重试成本。

## 39. Merge Queue 工作模型

```text
已满足入队检查的 PR
        ↓
最新 main + 前序队列变更 + 当前 PR
        ↓
新的 merge-group SHA → Fast + Full → 聚合检查
        ↓
平台执行集成；记录最终 main 与候选的关联
```

队列不会使失败证据消失。默认要求各 PR 满足入队条件，不使用放宽非通过 PR 的队列设置来遮掩 flaky failures。队列重建后记录新候选身份，不复制旧组绿色状态。[队列行为](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

## 40. Merge Queue 的触发与检查身份

Queue 使用的检查 workflow 必须同时覆盖 PR 与 `merge_group: checks_requested`，如 §28；缺少后者会使队列等不到检查。验证 checkout 的确是事件 SHA，不能手动切回单个 PR head。

主干 `push`、Nightly 和手动诊断使用不同 check 名称与目的，不抢占当前版本化准入 context。迁移时从真实 run 读取 check context、App、受测 SHA 与 workflow 来源，不能仅根据 UI 的 workflow / job 显示拼接猜测名称。

## 42. Flaky Tests 与失败治理

两种保证等级都保留初次失败、重跑及队列剔除原因。一次绿色结果不解释既有失败；需要修复与复验，或基础设施归因、有效隔离和补偿覆盖。新 commit / run / merge-group 不自动关闭旧失败，是否仍适用须有依据。

**standard：** 由可信维护者 / 审查者负责查看本次变更的失败记录、确认处置并记录在 PR / Issue 中。其失败处置依赖人工，不承诺 GitHub 原生 Required Check 能自动阻止“反复重跑直到绿灯”。出现未解决失败时，暂停相关 PR 的 Auto-merge / 入队并执行项目约定的阻塞措施；处置后才恢复。无可靠责任人时，不能将该流程描述为无人值守的失败治理。

**assured：** 按 §26.3 维护适用的未解决失败记录及关闭证据；按候选沿革、check ID、环境和受信任生产者关联。使用增量记录与有界核对，不要求每次合入从头重扫全部历史。记录数据源、处理水位、查询范围及截至时点；分页不完整、事件缺失、无法证明已追平或相关验证尚未结束时，阻塞或完成补查。归档不等于已解决，不能通过缩短查询窗口隐藏适用失败。

两种等级都不把无关历史失败永久阻塞当前候选；纯取消 / 未执行表示缺证，不虚构为产品缺陷。隔离须有责任人、问题链接、到期时间、风险接受和替代覆盖；无可接受补偿则继续阻塞。准入后新发现的问题进入主干修复、发布阻止及必要回滚流程。追踪 Flaky Rate、Queue Ejection Rate 与重复 Full 成本，优先修复导致队列反复重建的根因。

这是本工作流要求的工程政策；完整的机器化失败处置属于 assured 实现，§28 的阶段 Bash 并未实现它。GitHub 重跑使用原始事件 SHA / ref，run ID 保持、attempt 增加；重跑旧 run 不等于验证最新候选或策略。[重跑行为](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)、[运行身份](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)

## 43. Stacked PR

针对庞大且具备天然分层的架构演进，使用依赖链 PR（Stacked PRs），而非将数百行异构变更堆积在一个 PR 中：

```bash
# PR 1
git switch --no-track -c refactor/storage-engine origin/main

# PR 2 (基于 PR 1)
git switch --no-track -c feat/storage-api
gh pr create --base refactor/storage-engine --title "feat(storage): expose new storage API"

```

Stack 中目标为 feature 分支的 PR 不在 §28 的 main 过滤范围内；需要反馈时使用独立名称的 stack 检查。将其 retarget 到 main 后，重新生成并验证 main 的候选、复核 Diff 和依赖；父 PR 单独通过或旧 feature-base 检查不能替代该验证。未合入的前置 PR 仍是依赖，不因子 PR 局部通过而解除。

## 44. Release Automation 与制品身份

采用 Release Please 等工具管理版本、Changelog 与 Release PR，是可选的自动化实现。SemVer 与版本策略由项目契约决定；流水线仍须完成构建、验证和受控分发。

发布对象 SHOULD 是经过验证的不可变制品。记录 source revision、构建身份、环境、digest、验证结果和发布授权；环境间提升同一对象。重新构建得到的新制品须重新核对适用证据，不能仅因源码版本相同就继承全部结论。

---

## 45. 发布、验收与运行反馈

```text
Feature PR → main → Release PR → Tag / Release metadata
                       ↓
               构建与验证不可变制品
                       ↓
                 授权发布 / 分发
                       ↓
              安装与真实使用 / 运行观察
                       ↓
                能力验收与后续改进
```

Release 元数据创建不等于制品已可用。项目声明安装、兼容性、诊断、恢复与必要观察条件；CLI / library 可以在交付条件满足后验收，服务若要求观察窗口则等待相应证据。后续健康评估独立继续。

CHANGELOG 与 Tag 按已采用的发布流程维护；人工应急操作须可追溯，而不是一概禁止或绕过授权。PR 准入、制品发布和能力验收分别报告结果。

## 46. 分支清理

- 启用 GitHub `Automatically delete head branches`。
- 本地使用 `git fetch --prune` 与 `git worktree remove`。
- Squash 清理前核对指定 PR 已合并、local HEAD 等于该 PR 的已合并 head、工作树干净且没有执行器仍持有写权限，再删除本地分支；仅看到 PR merged 不足以执行 `git branch -D`。

## 47. 完整 Feature 生命周期实战

```bash
# 1. 同步最新状态并创建隔离工作区
git fetch --prune origin
git worktree add --no-track -b feat/registry-validation ../repo-registry-validation origin/main
cd ../repo-registry-validation

# 2. 开发与显式原子暂存
git status --short
git add path/to/new-file     # 新建文件显式加入
git add -p                   # 已有文件按 Hunk 暂存
git diff --cached --check
git commit -m "refactor: isolate validated inventory"

# 3. 本地快速与受影响验证；Full 按所选 Profile 执行
task quality:fast
export CI_PLAN_PATH="$(mktemp "${TMPDIR:-/tmp}/quality-plan.XXXXXX")"
task quality:plan
task quality:affected
git diff --check origin/main...HEAD

# 4. 推送并创建 Draft PR
git push --set-upstream origin HEAD
gh pr create --draft --title "feat(registry): validate node inventory atomically"

# 5. Fast 反馈后转为 Ready，再等待该阶段的必需检查
gh pr ready
gh pr checks --required --watch --fail-fast

# 6. 注册自动合并 (Auto-Merge Registration)
gh pr merge --squash --auto

# 7. 后置清理：先停止持有该工作区写权限的执行器。
# PR_URL 必须替换为本次创建、已记录的明确 PR URL。
PR_URL="https://github.com/OWNER/REPO/pull/NUMBER"
MERGED_AT="$(gh pr view "$PR_URL" --json mergedAt --jq '.mergedAt // empty')" || exit 1
MERGED_HEAD="$(gh pr view "$PR_URL" --json headRefOid --jq '.headRefOid')" || exit 1
LOCAL_HEAD="$(git rev-parse HEAD)" || exit 1
WORKTREE_STATUS="$(git status --porcelain --untracked-files=all)" || exit 1

if [[ -z "$MERGED_AT" || "$LOCAL_HEAD" != "$MERGED_HEAD" || -n "$WORKTREE_STATUS" ]]; then
  echo "Cleanup blocked: PR not merged, local commits differ, or workspace is dirty."
  exit 1
fi
# ignored 文件中需要保留的产物也须先保存；托管 worktree 使用其管理工具归档。

cd ../repo || exit 1
git worktree remove ../repo-registry-validation || exit 1
git branch -D feat/registry-validation
git fetch --prune

```

## 52. Agent 执行与准入权威

Agent 在有效任务授权内自主实现、验证、修复和提交候选；已有授权不需反复请求，技术访问能力也不产生新的业务授权。

执行完成、验证结论、语义审查、平台准入与能力接受分别记录。模型的总结不是可信 CI；CI 变绿不是维护者的产品 / 架构接受；Ruleset 放行也不表示获得生产发布权限。高风险或关键契约变更按项目责任升级。

执行器中断、push / 建 PR / 合并请求超时时，先查询远端实际效果，无法确认保持 unknown，不盲目重复外部动作。新会话或新 Attempt 不使旧副作用失效。失联写入者未确认停止或未可靠撤销写权限前，不向同一可变工作区授予第二写入者。

## 55. 关键 Anti-Patterns 清单

1. **长期存在的 `develop` 分支**（制造集成壁垒与发版黑洞）。
2. **直接 Push 代码至 `main`**（绕过自动化安全审计）。
3. **在 `main` 分支执行 Force Push**（破坏历史一致性）。
4. **强迫每个 PR 在合并前反复手动 Rebase**（产生无意义的 Rebase Tax）。
5. **在产生 Required Check 的普通 workflow 顶层配置 `paths` 过滤**（可能使必需检查一直 pending）；组织级 Required Workflow 的过滤行为另见 §30。
6. **在 CI YAML 中直接维护全套 Lint/Test 脚本**（导致本地与 CI 逻辑脱节）。
7. **CODEOWNERS 范围过度扩大给少数核心成员**（成为全局审查瓶颈）。
8. **面对 Flaky Test 盲目重跑直到绿灯**（掩盖系统不确定性）。
9. **因“Commit 分得很清晰”而放任数千行大 PR 合入**（破坏 PR 语义内聚性）。
10. **固定 SHA 后不维护版本与安全更新**（缺乏更新追踪）。
11. **无强制队列却把 Full 只放在 merge_group**（Fast 可能成为唯一准入检查）。
12. **把所有兼容、安全、性能检查移到 nightly**（遗漏契约必需的合入前覆盖）。
13. **用缓存、旧 SHA 绿灯或单次重跑代替当前证据**（掩盖对象变化与未处置失败）。

## 56. 成熟度模型

| Stage       | 定位                                    | 核心能力                                                                         |
| ----------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| **Stage 0** | **Local Discipline**                    | Clean workspace、`fetch --prune`、`rerere`、Atomic diff、本地 `task quality`     |
| **Stage 1** | **Repository Discipline**               | Short-lived branch、PR-only、Squash-only、Ruleset、PR Title 契约、对话闭环       |
| **Stage 2** | **Reproducible Verification Control Plane** | 仓库自治 Quality 逻辑、分阶段聚合 `Quality` Gate、Action SHA Pinning、策略文件受保护 |
| **Stage 3** | **Automated Integration Control Plane** | 按条件选择集成 Profile、不可变制品、受控发布、能力反馈与成本改进        |

## 57. Stage 0 — Local Discipline

- 团队成员统一配置 `fetch.prune`、`rerere`、`push.autoSetupRemote` 与 `pull.ff=only`。
- 养成基于 `git diff --check origin/main...HEAD` 与本地 `task quality:fast` 的自检习惯。

---

## 58. Stage 1 — Repository Discipline

- 确立 `main` 为唯一长期分支，全面推行 PR-only、Squash-only 与 PR Title 规范。
- 启用自动删除 head 分支与对话全部 resolved 方可合入的约束。

---

## 59. Stage 2 — 可复现验证与证据

- 分别选定集成方式与保证等级，建立阶段明确的版本化门禁；standard 落实可信审查及原生保护，assured 另接入 §26.3。
- 实施 Fast / Plan / Affected / Full，PR-full 用一份 Full 满足计划，未知范围升级 Full，异常聚合 fail-closed。
- Action 固定完整 SHA；选择器、Profile 和工作流纳入策略面保护。
- 明确平台 / 兼容性覆盖及真实环境，不将文档配置当作运行证据。

---

## 60. Stage 3 — 自动集成与持续改进

- 按可用性和实际瓶颈选择 PR-full + Auto-merge 或强制 Queue。
- 在已授权范围按需并行，隔离 Worktree 与运行资源，不固定增加 Agent 数量。
- 连接不可变制品、发布、能力验收和运行反馈。
- 按合格交付总成本及质量回归评估 CI 优化，不以安装更多工具判断成熟度。

## 61. 测量反馈时间、计算成本与质量

按 Draft / Ready / merge-group / Nightly / Release 分开统计 p50 / p95，至少拆分 Queue、Setup、Dependency Restore、Compile、Test、Artifact Upload。保留被取消、失败、重跑与队列重建的成本。

| 目标 | 指标与解释 |
| --- | --- |
| 开发反馈 | push 到可用 Fast 结果的耗时，含排队 |
| 合格集成 | Ready 到合入时长、Full 次数、Queue 剔除及重建次数；分别统计代码 / base 变化与纯 metadata 编辑导致的重启 |
| 资源效率 | 每个合格 PR / 能力的总 runner-minutes、账单费用、存储与人工介入；单列重复 Full、重复构建和高保证核验 / 历史查询成本 |
| 选择质量 | Affected 的 Full 回退率、漏选回归、误选工作及节省量 |
| 产品与工程质量 | 逃逸缺陷、返工、Change Failure / Rollback Rate、安装与运行问题 |

并行 Job 的 wall-clock 不能当作 runner-minutes，取消后的计费时间也不能记为零。先用观测确定瓶颈，再选择缓存、依赖预构建、测试分片或更快 Runner；用代表性任务和相同质量条件比较前后结果。

例如“8 次 15 分钟 Full”与“8 次 2 分钟 Fast + 1 次 15 分钟 Full”只有在每次运行都占一个同价 Runner、没有重建重跑等额外成本的假设下，才分别是 120 与 31 runner-minutes；不能把这组算术当成本仓库的实测收益。

## 62. 采用与迁移验收

### 62.1 推荐起点

默认采用 PR-full；在可信维护者和独立审查前提下选择 standard，威胁模型需要时选择 assured。先实现 Draft Fast 和 Plan → Execution、消除重复 Full，再测量缓存和构建复用收益；无需为常规协作先自建高保证系统。Queue 按可用性和实测收益采用，`task quality` 保持 Full 语义。仍须通过真实仓库验证必要覆盖未减少、每个合格 PR 的等待与总成本下降；语法检查不能证明提速收益。

### 62.2 Profile / 策略代次迁移顺序

本节适用于 §27 判定旧绿灯不再可接受、保证等级 / 生产者 / 集成方式改变等准入契约迁移；普通验证器 revision 更新按正常 PR 流程验证，不自动进入全仓库维护窗口。迁移必须同时处理代码、检查身份和平台规则，不能靠一次 YAML diff 原子完成。Queue PR 的绿灯只代表入队；同 SHA 的旧绿灯可能仍存在，重新运行旧 run 也不保证采用新策略。

1. **登记旧新绑定。** 记录 Profile、policy epoch、Required context、App / workflow 来源、规则实际状态、权限、覆盖和回退目标；新策略使用未被旧绿灯占用的新 context，例如 `queue-standard-v1` 或回退用的 `pr-full-standard-v2`。
2. **暂停合入并核对在途操作。** 停止普通候选的新入队及 auto-merge 请求，排空或移除在途队列，并采用仓库可执行的写入 / 合入限制阻止普通身份继续合入；仅公告“暂停”不算生效。确认无未知 merge 操作，记录维护窗口负责人和解除条件。不能用临时取消 Required Checks 来制造维护窗口。
3. **在旧保护仍有效时准备新策略。** 维护窗口仅放行已审查的策略候选，仍走旧检查和旧集成路径；旧路径为 Queue 时，仅该候选可受控入队。保留旧必需验证，迁移期间可双跑 Full / 双 context。先用受控候选实际运行新检查和失败路径，再将它加入 Required Checks；平台选择检查可能要求它在最近七天内成功运行。assured 骨架未完成独立核验绑定时故意不会成功；standard 则须完成其仓库入口和可信审查 / 保护接入。两者都不能为了出现在选择器中临时发伪造绿灯。
4. **切换平台约束。** PR-full → Queue 时，先强制队列和对应 merge-group 检查，再采用 Queue 的 PR 轻验证；Queue → PR-full 时，先要求新的 PR-full context、up-to-date 和全部 Full，后停用队列。新检查成为必需且已核验后，才撤下旧 context。规则叠加期间如果没有候选能满足全部要求，继续暂停并修复，不能临时旁路放行。
5. **刷新全部仍开放的候选。** 让其采用新 workflow / 策略并针对当前 base 重验；需要时更新分支或创建新提交。不能用“重跑旧 run”代替策略刷新。清除旧队列候选，重建新组；核对当前 context 的生产者、SHA、覆盖、失败处置及正常身份直接合入受阻。
6. **解除暂停并记录采用。** 只有 §62.3 对所选路径的实际验收通过，才恢复 auto-merge / 入队，并记录固定文档摘要、策略代次、配置与运行证据。失败时保持暂停；回退本身也是一次新代次迁移，不能恢复旧名字就假定旧证据有效。

已有绿色 PR、已排队 PR、未含新 workflow 的旧分支都必须纳入迁移清单。若仓库无法提供可靠维护窗口或新旧规则并存路径，先在隔离仓库演练，继续使用当前已验证策略；不要在线试错。

### 62.3 真实仓库必须执行的迁移案例

| 案例 | 预期结果 |
| --- | --- |
| Draft push；随后无新 commit 转 Ready | Draft 仅 Fast，不准入；Ready 生成计划并执行对应模式 |
| Ready 再 push、退回 Draft、改目标分支；重跑旧 run | 只采信当前候选 / 目标 / 阶段；旧 run 可能取消新 run 时恢复当前验证，不按完成时间选证据 |
| Plan 失败 / 缺失 / 格式非法；必需执行失败、取消或超时 | 聚合非成功；不能将缺计划解释为无需测试 |
| 未知 Profile / 执行模式、空选择器输出 | 拒绝；不能用 Full 代替合法策略或计划 |
| 未知路径、缺失历史 / 不完整 diff | 生成合法的 Full 计划后执行 Full，或失败；不能静默跳过 |
| 改依赖锁、CI、选择器、共享库、删除或重命名文件 | 覆盖受影响范围 / 反向依赖；必要时 Full；策略变更按所选保证等级审查 / 核验 |
| 两个 PR 单独通过但组合失败 | merge-group Full 拒绝；无队列时 up-to-date 后重验组合 |
| 队列前序变化、同时构建多个组 | 新组绑定新 SHA；Actions 不互相取消不同组 |
| 尝试直接合并 Queue PR；管理员 / Bot 走旁路 | 正常身份均受实际规则约束；授权应急例外另记，不能报告为门禁通过 |
| Queue → PR-full 时仍有绿色 PR / 在途队列 | 暂停合入；旧 Queue context 不满足新 PR-full context；Full 补齐前不能直接合入 |
| PR-full → Queue；旧分支仍使用旧 workflow | 队列先强制，新 context 成为必需；刷新旧候选后才恢复合入 |
| 同 SHA 先失败后重跑通过，或队列重建后通过 | standard 验证责任人阻塞 / 处置流程；assured 验证适用未解决失败的机器阻塞；均保留原始证据 |
| 删除必需 matrix、只输出 exit 0、缺失报告、伪造同名 check | standard 验证独立审查和策略保护；assured 另验证机器化覆盖 / 来源拒绝，不能把前者报告为后者 |
| 新 context 尚未生效、规则 Disabled、来源不符；assured 核验器不可用 | 保持阻塞；不能删除旧规则来使迁移“成功” |
| PR-full 计划要求 Full；或 Affected 要求全部被 Full 覆盖 | Plan 不执行测试，执行入口只运行一次 Full；覆盖不匹配则补齐 / 拒绝 |
| Queue PR 的未知路径 / 图缺失，及对应 merge-group | PR 的 Affected 入口只升级一次 Full；merge-group 独立运行组合 Full，不能跨对象去重 |
| 新增普通回归测试；新增所有开放候选必须通过的紧急检查 | 前者记录 revision 并正常验证；后者使不足旧证据失效，不能机械地一律迁移或一律复用 |
| 纯描述编辑发生在 Full 运行期间 | 记录当前保守重跑成本；后续 metadata 分流须证明不取消代码验证，也不伪造 / 覆盖准入结果 |
| fork PR / 不可信代码 | 无生产 secrets / 写权限；不能污染特权构建来源 |
| Nightly 未运行 / 失败；发布了不同 digest | 必需发布证据仍缺失或不适用，不因以前绿色而放行 |

表格是实施验收要求，不是已完成测试的声明。本稿本地检查不覆盖真实 GitHub 事件、Ruleset、审查执行或迁移维护窗口；assured 的独立核验和身份隔离也须由消费仓库实测。只执行适用等级的案例，报告采用等级及限制，不把文档覆盖视为已通过。

## 63. 完整工程系统中的仓库工作流

```text
问题 / 使用场景 → 探索与能力契约
                         ↓
              一个或多个语义内聚 PR
                         ↓
             Fast → Plan → 审查
                         ↓
        PR-full 或强制 Queue 的候选 Full
                         ↓
                 main 集成事实
                         ↓
          不可变制品 → 受控发布 / 分发
                         ↓
           真实使用、能力验收、运行反馈
                         └────────→ 下一轮改进
```

GitHub、执行器、CI 和计算平台是可替换组成部分。产品、设计、实现、交付维护四维质量共同约束结果；本工作流优化仓库环节，不能替代完整系统的目标和接受责任。
